# Colour science and correction

Scope: colour spaces, transfer curves, YUV ranges, chroma subsampling, colour tags, scopes, white balance, exposure, contrast, primary and secondary correction, qualifiers and windows, shot matching, HDR (PQ/HLG/HDR10/Dolby Vision), ACES/OCIO and colour space transforms, done the ffmpeg way. Named creative looks are out of scope (category 03).
Researched 2026-10-24 via agent-reach (Exa) web search, official docs and local tests.

Notes: tests ran on ffmpeg 6.1.1 (Ubuntu build) with synthetic testsrc2 clips (8-bit BT.709, 10-bit HLG and 10-bit PQ HEVC made with x265). "(tested here 2026-10-24)" means the command ran without error here. It says nothing about how the result looks. Where a doc describes newer ffmpeg (7.x/8.x) behaviour, the skill says what 6.1 did here. File names (in.mp4, out.mp4) are placeholders.

## Colour tags: read, keep, retag, convert

801. **Read all five colour properties first** — every decoded frame needs primaries, transfer, matrix and range to become light, plus chroma location. If any is missing or wrong the encode still "works" but colours shift, blacks lift or crush, or HDR looks flat. **How:** `ffprobe -v error -select_streams v:0 -show_entries stream=pix_fmt,color_range,color_space,color_transfer,color_primaries,chroma_location -of default=nw=1 in.mp4` (tested here 2026-10-24) [Encode Wiki, https://encode.wiki/reference/colorimetry/intro, checked 2026-10-24]
802. **Look at the first frame for HDR side data** — mastering display, content light level, Dolby Vision and HDR10+ data usually sit per frame in the bitstream, not on the stream. **How:** `ffprobe -v error -select_streams v:0 -read_intervals "%+#1" -show_frames in.mp4` and look for `side_data_type=Mastering display metadata` / `Content light level metadata` (tested here 2026-10-24 on an x265 HDR10 clip: printed red_x=34000/50000, max_luminance=10000000/10000, max_content=1000, max_average=400) [Encode Wiki, https://encode.wiki/reference/colorimetry/intro, checked 2026-10-24]
803. **Tagging is not converting** — there are three different jobs: preserve (keep samples and tags), retag (change only the metadata, right only when the source was mis-tagged), convert (change the samples, then tag the new system). Writing bt709 onto BT.601 pixels makes the colours wrong. Tagging PQ as bt709 does not tone-map it. **How:** decide which of the three you are doing before writing any filter. Use `setparams` to retag and `zscale`/`scale`/`colorspace` to convert. [Encode Wiki, https://encode.wiki/reference/colorimetry/intro, checked 2026-10-24]
804. **Players guess untagged video differently** — mpv 0.41 picks the BT.709 matrix when width >= 1280 or height > 576, otherwise BT.601. It picks the transfer as BT.1886 for limited range and sRGB for full range. So an untagged 720x480 file can look right in one player and slightly green in another. **How:** tag every export, and never assume an untagged source is BT.709. Check where it came from. [Encode Wiki, https://encode.wiki/reference/colorimetry/intro, checked 2026-10-24]
805. **Guess the truth of unknown tags from the source** — DVDs are BT.601 (smpte170m NTSC, bt470bg PAL), HD Blu-ray/broadcast are BT.709, UHD Blu-ray HDR is BT.2020 + PQ. A 1080p upscale of a DVD can still carry BT.601 colours. **How:** use the origin, not the resolution, to pick values for `setparams`. [Encode Wiki, https://encode.wiki/guides/preserve-color-and-hdr, checked 2026-10-24]
806. **Retag frames with setparams** — `setparams` marks colour range, primaries, trc and colorspace on the frames without changing the input pixels. It affects how later filters/encoders treat the frame. **How:** `ffmpeg -i in.mp4 -vf setparams=color_primaries=smpte170m:color_trc=smpte170m:colorspace=smpte170m:range=tv -c:v libx264 -crf 18 out.mp4` (tested here 2026-10-24; ffprobe then showed tv/smpte170m on all three) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#setparams, checked 2026-10-24] [Encode Wiki, https://encode.wiki/guides/preserve-color-and-hdr, checked 2026-10-24]
807. **Retag H.264 without re-encoding** — the h264_metadata bitstream filter rewrites colour_primaries, transfer_characteristics and matrix_coefficients in the VUI (H.273 numbers). Pass the same values as output options so the container agrees. **How:** `ffmpeg -i in.mp4 -c copy -bsf:v h264_metadata=colour_primaries=1:transfer_characteristics=1:matrix_coefficients=1 -color_primaries bt709 -color_trc bt709 -colorspace bt709 out.mp4` (tested here 2026-10-24) [ffmpeg bsf docs, https://ffmpeg.org/ffmpeg-bitstream-filters.html#h264_005fmetadata, checked 2026-10-24] [Encode Wiki, https://encode.wiki/guides/preserve-color-and-hdr, checked 2026-10-24]
808. **Retag HEVC without re-encoding** — hevc_metadata has the same colour description options (and video_full_range_flag, chroma_sample_loc_type). **How:** `ffmpeg -i in.mp4 -c copy -bsf:v hevc_metadata=colour_primaries=9:transfer_characteristics=18:matrix_coefficients=9 out.mp4` (tested here 2026-10-24) [ffmpeg bsf docs, https://ffmpeg.org/ffmpeg-bitstream-filters.html#hevc_005fmetadata, checked 2026-10-24]
809. **Fix only the range flag in the bitstream** — when samples are limited but the file is tagged pc, flip `video_full_range_flag` and set `-color_range` so the container matches. **How:** `ffmpeg -i in.mp4 -c copy -bsf:v h264_metadata=video_full_range_flag=0 -color_range tv out.mp4` (tested here 2026-10-24) [Encode Wiki, https://encode.wiki/reference/colorimetry/range, checked 2026-10-24]
810. **Bitstream filters leave the container colour fields alone** — from MKV/MP4 input, ffmpeg copies the old container values (Matroska Colour elements, MP4 colr box), so ffprobe can keep showing the old tags. For an existing MKV, mkvpropedit fixes them in place. Remuxing with mkvmerge keeps the old values. **How:** `mkvpropedit out.mkv --edit track:v1 --set color-transfer-characteristics=1 --set color-primaries=1 --set color-matrix-coefficients=1` (needs mkvtoolnix, missing) [Encode Wiki, https://encode.wiki/guides/preserve-color-and-hdr, checked 2026-10-24]
811. **Output colour options behave differently by ffmpeg version** — in ffmpeg 7.1 and later the encoder takes colour properties from the filtered frames: `-color_primaries`/`-color_trc` get overwritten, and `-colorspace`/`-color_range` can trigger an auto-inserted scaler that converts samples. Encode Wiki says to tag with setparams and convert with an explicit filter. **How:** in this repo's ffmpeg 6.1, `-colorspace 1 -color_primaries 1 -color_trc 1` did tag the output. For portable scripts, still use `setparams` (tested here 2026-10-24) [Encode Wiki, https://encode.wiki/guides/preserve-color-and-hdr, checked 2026-10-24] [Canva Engineering, https://www.canva.dev/blog/engineering/a-journey-through-colour-space-with-ffmpeg/, checked 2026-10-24]
812. **Tag options never move pixels** — `-colorspace 1 -color_primaries 1 -color_trc 1` only add meta information. They do not transform the colour space of the video. **How:** pair the tags with a converting filter, e.g. `ffmpeg -i in.png -pix_fmt yuv420p -vf colorspace=all=bt709:iall=bt601-6-625:fast=1 -colorspace 1 -color_primaries 1 -color_trc 1 out.mp4` (tested here 2026-10-24) [Canva Engineering, https://www.canva.dev/blog/engineering/a-journey-through-colour-space-with-ffmpeg/, checked 2026-10-24]
813. **H.273 code points to remember** — primaries 1 = BT.709/sRGB, 9 = BT.2020, 11 = DCI-P3 (DCI white), 12 = P3-D65/Display P3. Transfer 1 = BT.709, 13 = sRGB, 16 = PQ, 18 = HLG. Matrix 0 = GBR (RGB), 1 = BT.709, 5/6 = BT.601, 9 = BT.2020 NCL, 14 = ICtCp. **How:** use these numbers in h264_metadata/hevc_metadata. [Encode Wiki, https://encode.wiki/reference/colorimetry/primaries, checked 2026-10-24] [Encode Wiki, https://encode.wiki/reference/colorimetry/transfer, checked 2026-10-24] [Encode Wiki, https://encode.wiki/reference/colorimetry/matrix, checked 2026-10-24]
814. **"1-1-1" means a Rec.709 SDR master** — QuickTime `colr` atom type `nclc` stores three indexes (primaries, transfer, matrix). MP4 `nclx` adds a full_range flag. 1-1-1 is the right tag for HD SDR pixels graded in Rec.709 and wrong for a P3 grade. **How:** check the three values with ffprobe before sending a MOV. [Versely, https://www.versely.studio/blog/container-color-tags-nclc-and-colr-atoms, checked 2026-10-24]
815. **Transfer codes 1, 6, 14 and 15 are the same curve** — BT.709, BT.601, BT.2020-10 and BT.2020-12 describe one curve. Use the one that matches the system. mpv displays all four with BT.1886. **How:** don't "fix" a 6 to a 1 expecting a visual change. [Encode Wiki, https://encode.wiki/reference/colorimetry/transfer, checked 2026-10-24]
816. **Pure-2.2 content can be tagged bt470m** — sRGB (13) has a linear toe while many displays and much RGB content use a pure 2.2 power curve. If content was made for pure 2.2, tag transfer 4 (bt470m, "assumed display gamma 2.2"). **How:** `setparams=color_trc=bt470m` (option listed in setparams docs) [Encode Wiki, https://encode.wiki/reference/colorimetry/transfer, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#setparams, checked 2026-10-24]
817. **Tag checklist after every export** — run the same ffprobe on source and output and compare. Then watch both side by side in a player that honours tags (mpv), looking at skin, saturated reds/greens and shadow detail. **How:** stream ffprobe from skill 801 plus frame ffprobe from 802 on both files. [Encode Wiki, https://encode.wiki/guides/preserve-color-and-hdr, checked 2026-10-24]
818. **Standalone x264/x265 pipes lose all colour info** — Y4M carries no primaries, transfer or matrix, so pass `--colorprim/--transfer/--colormatrix/--range/--chromaloc` yourself. x265 4.3 ignores the Y4M full-range flag and tags limited. **How:** inside ffmpeg use `-x264-params colorprim=bt709:transfer=bt709:colormatrix=bt709:range=tv:chromaloc=0` (tested here 2026-10-24) [Encode Wiki, https://encode.wiki/guides/preserve-color-and-hdr, checked 2026-10-24]
819. **x265 signal-type presets** — `--video-signal-type-preset` sets primaries, transfer, matrix, range and chroma location in one go (e.g. BT2100_HLG_YCC = bt2020 / arib-std-b67 / bt2020nc / limited / chromaloc 2). It overrides individual VUI options. **How:** `ffmpeg -i in.mp4 -c:v libx265 -pix_fmt yuv420p10le -x265-params "video-signal-type-preset=BT2100_HLG_YCC" out.mp4` (tested here 2026-10-24) [x265 docs, https://x265.readthedocs.io/en/master/cli.html, checked 2026-10-24]
820. **YouTube standardises unclear SDR tags** — unspecified TRC → BT.709. Unknown matrix and primaries → BT.709. A 601/709 mix is made consistent by the matrix. Full range is converted to limited, BT.2020 without an HDR transfer is converted to BT.709 8-bit, and an RGB matrix upload is not recommended. **How:** upload SDR tagged 1-1-1 limited (`setparams=color_primaries=bt709:color_trc=bt709:colorspace=bt709:range=tv`). [YouTube Help, https://support.google.com/youtube/answer/1722171?hl=en, checked 2026-10-24]

## Matrix (YCbCr) and RGB↔YUV conversion

821. **Luma is a weighted sum set by KR and KB** — Y′ = KR·R′ + (1−KR−KB)·G′ + KB·B′. BT.709 uses KR 0.2126/KB 0.0722, BT.601 0.299/0.114, BT.2020 NCL 0.2627/0.0593. ffprobe reports the matrix as color_space. **How:** read `color_space` with ffprobe. [Encode Wiki, https://encode.wiki/reference/colorimetry/matrix, checked 2026-10-24]
822. **Luma is not luminance** — luma (Y′) is a weighted sum of gamma-compressed R′G′B′. Relative luminance (Y) is a weighted sum of linear RGB. SMPTE EG 28 uses Y′ for luma and Y for luminance. **How:** remember signalstats YAVG is luma code values, not light. [Wikipedia, https://en.wikipedia.org/wiki/Luma_(video), checked 2026-10-24]
823. **A wrong matrix shifts saturated colours, not greys** — decoding with the wrong matrix barely changes greys but moves reds, greens and skin. You often only see it next to the source. **How:** compare a skin crop of source vs encode with `hstack`. [Encode Wiki, https://encode.wiki/reference/colorimetry/matrix, checked 2026-10-24] [Portrait Displays, https://www.portrait.com/resource-center/understanding-the-color-decoder/, checked 2026-10-24]
824. **Which tag mistakes you can see** — wrong primaries (SMPTE 170M vs Rec.709) is almost undetectable. Wrong transfer (sRGB vs Rec.709) shows side by side. Wrong Y′CbCr encoding (601 vs 709) is easy to see. **How:** fix the matrix first when tags are in doubt. [GStreamer conf / Hans Verkuil, https://gstreamer.freedesktop.org/data/events/gstreamer-conference/2015/Hans%20Verkuil%20-%20Colorspaces%20and%20HDMI.pdf, checked 2026-10-24]
825. **PNG/RGB to video defaults to the BT.601 matrix** — ffmpeg converts RGB input (PNG frames, screen captures) to YUV with BT.601 and leaves it untagged, and HD players then decode it as BT.709. **How:** `ffmpeg -i in.png -vf scale=out_color_matrix=bt709,format=yuv420p,setparams=color_primaries=bt709:color_trc=bt709:colorspace=bt709 -c:v libx264 out.mkv` (tested here 2026-10-24; on 6.1 the colorspace tag stayed unknown until `colorspace=bt709` was added to setparams) [Encode Wiki, https://encode.wiki/reference/colorimetry/matrix, checked 2026-10-24] [ffmpeg-tests, https://richardssam.github.io/ffmpeg-tests/ColorPreservation.html, checked 2026-10-24]
826. **Convert the matrix when SD becomes HD** — upscaling a DVD to 1080p and tagging BT.709 without converting shifts greens and skin. zscale takes the input interpretation explicitly. **How:** `ffmpeg -i dvd.mkv -vf zscale=w=1440:h=1080:f=spline36:min=170m:pin=170m:tin=601:m=709:p=709:t=709 -c:v libx264 -crf 18 out.mp4` (tested here 2026-10-24). For PAL use `min=470bg:pin=bt470bg`. [Encode Wiki, https://encode.wiki/guides/preserve-color-and-hdr, checked 2026-10-24]
827. **scale converts only the matrix** — the built-in scale filter converts the matrix, so keep the source's primaries and transfer tags when you use it. **How:** `ffmpeg -i dvd.mkv -vf scale=1440:1080:in_color_matrix=bt601:out_color_matrix=bt709,setparams=color_primaries=smpte170m:color_trc=smpte170m -c:v libx264 -crf 18 out.mp4` (tested here 2026-10-24) [Encode Wiki, https://encode.wiki/guides/preserve-color-and-hdr, checked 2026-10-24]
828. **colormatrix is the basic matrix filter** — `colormatrix=src:dst` converts between bt709, fcc, bt601, bt470, bt470bg, smpte170m, smpte240m and bt2020. It does not set tags itself. **How:** `ffmpeg -i in.mp4 -vf colormatrix=bt601:bt709 -c:v libx264 out.mp4` then tag (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#colormatrix, checked 2026-10-24] [Video SE, https://video.stackexchange.com/questions/16840/ffmpeg-explicitly-tag-h-264-as-bt-601-rather-than-leaving-unspecified, checked 2026-10-24]
829. **colorspace filter: fast=1 equals colormatrix** — `fast=1` skips gamma/primary correction (less CPU, mathematically incorrect). It gives output compatible with colormatrix. **How:** `colorspace=all=bt709:iall=bt601-6-625:fast=1` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#colorspace, checked 2026-10-24]
830. **colorspace needs input tags or iall** — the filter needs even frame size. If the input transfer/space/primaries/range are missing it logs an error and does not convert. Override with `iall`, `ispace`, `iprimaries`, `itrc`, `irange`. **How:** `colorspace=all=bt709:iall=bt601-6-625` for an untagged SD source. [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#colorspace, checked 2026-10-24]
831. **colorspace can write 10-bit output** — `format=` takes yuv420p/422p/444p in 8, 10 and 12 bit. **How:** `ffmpeg -i in.mp4 -vf colorspace=all=bt709:format=yuv420p10 -c:v libx264 out.mp4` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#colorspace, checked 2026-10-24]
832. **colorspace dithering and white-point adaptation** — `dither=fsb` gives Floyd-Steinberg dithering. `wpadapt=bradford|vonkries|identity` sets white-point adaptation when primaries change. **How:** `colorspace=all=bt709:iall=bt2020:format=yuv420p:dither=fsb` and `colorspace=all=bt709:iall=bt2020:wpadapt=bradford` (both tested here 2026-10-24). `clipgamut=rgb` is in current docs but "Option not found" on 6.1. [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#colorspace, checked 2026-10-24]
833. **Accurate swscale flags for colour conversion** — the ffmpeg-tests author recommends the scale filter with `spline+accurate_rnd+full_chroma_int+full_chroma_inp`. **How:** `ffmpeg -i in.png -sws_flags spline+accurate_rnd+full_chroma_int+full_chroma_inp -vf scale=in_range=full:in_color_matrix=bt709:out_range=tv:out_color_matrix=bt709 -pix_fmt yuv444p10le -c:v libx264 -qp 0 -color_range tv -colorspace bt709 -color_primaries bt709 -color_trc bt709 out.mp4` (tested here 2026-10-24) [ffmpeg-tests, https://richardssam.github.io/ffmpeg-tests/ColorPreservation.html, checked 2026-10-24] [ffmpeg scaler docs, https://ffmpeg.org/ffmpeg-scaler.html#Scaler-Options, checked 2026-10-24]
834. **swscale dither choice** — `sws_dither` accepts auto (default), bayer, ed (error diffusion), a_dither and x_dither. **How:** `ffmpeg -i in10bit.mp4 -sws_dither ed -vf format=yuv420p -c:v libx264 out.mp4` (tested here 2026-10-24) [ffmpeg scaler docs, https://ffmpeg.org/ffmpeg-scaler.html#Scaler-Options, checked 2026-10-24]
835. **BT.2020 C and NCL are different signals** — bt2020nc (9) is normal for UHD SDR, HDR10 and HLG. bt2020c (10) needs different maths, so switching 9↔10 is never a fix. ICtCp (14) is a separate representation. **How:** leave 9 alone on phone/HDR files. [Encode Wiki, https://encode.wiki/reference/colorimetry/matrix, checked 2026-10-24]
836. **ICtCp basics** — ICtCp (BT.2100) is RGB→LMS (3×3), then PQ or HLG nonlinearity, then another 3×3. I is intensity, CT blue-yellow, CP red-green. It is mostly used with PQ. BT.2408 prefers Y′CbCr for HLG and notes compatibility limits for ICtCp. **How:** treat `color_space=ictcp` files as special and don't retag them. [Wikipedia, https://en.wikipedia.org/wiki/ICtCp, checked 2026-10-24] [ITU-R BT.2408-7, https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2408-7-2023-PDF-E.pdf, checked 2026-10-24]

## Range (limited/full)

837. **Range code-value table** — 8-bit limited: luma 16–235, chroma 16–240. 10-bit limited: 64–940 / 64–960. Full: 0–255 / 0–1023. Neutral chroma is 128 (8-bit) and 512 (10-bit). **How:** use 128/512 as the "no colour" target when reading UAVG/VAVG. [Encode Wiki, https://encode.wiki/reference/colorimetry/range, checked 2026-10-24]
838. **Deliver limited range** — Blu-ray, UHD Blu-ray (incl. HDR), broadcast and streaming are limited range almost without exception. Full range turns up in screen recordings, some phone/webcam footage, JPEG-derived video and RGB sources. **How:** convert full-range phone/screen clips to limited for delivery (next skills). [Encode Wiki, https://encode.wiki/reference/colorimetry/range, checked 2026-10-24]
839. **Don't clamp a source for overshoot** — values below 16 or above 235 can legitimately appear in limited-range video (camera/filter overshoot). Players clip them on display, but encoders and filters normally keep them. **How:** measure before deciding to legalise. [Encode Wiki, https://encode.wiki/reference/colorimetry/range, checked 2026-10-24]
840. **Rule out the player before fixing range** — Encode Wiki: GPU drivers and TVs have their own range settings that produce the same washed-out or crushed symptoms as a file mix-up, so check the player/display first. **How:** compare the file's signalstats YMIN/YMAX with what the screen shows before re-encoding anything. [Encode Wiki, https://encode.wiki/reference/colorimetry/range, checked 2026-10-24]
841. **Prove the range from samples, not one frame** — measure a scene that should hold black and white (credits). YMIN near 16 / YMAX near 235 means limited. 0 / 255 means full. A dim scene proves nothing. **How:** `ffmpeg -ss 00:10:00 -i in.mkv -frames:v 100 -vf "signalstats,metadata=mode=print:file=-" -f null - | grep -E "YMIN|YMAX"` (pattern tested here 2026-10-24 with file= output) [Encode Wiki, https://encode.wiki/reference/colorimetry/range, checked 2026-10-24]
842. **Full→limited with scale needs format=yuv420p** — ffmpeg decodes 8-bit full-range H.264/HEVC as legacy yuvj420p. Without `format=yuv420p`, scale silently does nothing. **How:** `ffmpeg -i full.mp4 -vf scale=out_range=limited,format=yuv420p -c:v libx264 -crf 18 out.mp4` (tested here 2026-10-24: YMIN/YMAX went from 0/239 to about 13/218, but on 6.1 the range tag came out unknown) [Encode Wiki, https://encode.wiki/reference/colorimetry/range, checked 2026-10-24]
843. **Fix the unknown range tag on 6.1** — here neither `setparams=range=tv` nor `-color_range tv` nor `-x264-params range=tv` tagged the converted file. A copy pass with h264_metadata did. **How:** `ffmpeg -i out.mp4 -c copy -bsf:v h264_metadata=video_full_range_flag=0 -color_range tv out_tv.mp4` (tested here 2026-10-24: ffprobe color_range=tv) [Encode Wiki, https://encode.wiki/reference/colorimetry/range, checked 2026-10-24]
844. **zscale converts range but may keep the pc tag** — zscale=range=limited converts the samples but can leave the output tagged full range. **How:** `ffmpeg -i full.mp4 -vf zscale=rangein=full:range=limited,format=yuv420p -c:v libx264 out.mp4` (tested here 2026-10-24), then retag as in 843. [Encode Wiki, https://encode.wiki/guides/preserve-color-and-hdr, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#zscale-1, checked 2026-10-24]
845. **yuvj formats are deprecated** — yuvj420p is the legacy name for full-range 8-bit. ffmpeg developers have worked to remove YUVJ in favour of yuv420p plus a range tag. **How:** write full range as `format=yuv420p,setparams=range=pc` (tested here 2026-10-24; ffprobe still reported yuvj420p/pc on 6.1) [FFmpeg-devel, https://ffmpeg.org/pipermail/ffmpeg-devel/2023-November/316818.html, checked 2026-10-24] [Encode Wiki, https://encode.wiki/reference/colorimetry/format, checked 2026-10-24]
846. **Matroska range numbers differ** — Matroska's Range element uses 1 = broadcast (limited), 2 = full. The H.273 bitstream flag uses 0 = limited, 1 = full. **How:** mkvmerge `--color-range 0:1` means limited. [Encode Wiki, https://encode.wiki/reference/colorimetry/range, checked 2026-10-24]
847. **Narrow range keeps headroom, full range has none** — BT.2100 narrow range keeps super-whites and sub-blacks for overshoots from resizing, filtering and compression, and clipping them adds distortion. BT.2408 says full range should not be used for HLG production/exchange. Full-range PQ only when all parties agree. **How:** keep HDR exports `range=tv`. [ITU-R BT.2408-7, https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2408-7-2023-PDF-E.pdf, checked 2026-10-24]
848. **Legalise only with care** — EBU R103 (2000): accept material when matrixed R, G, B lie within −5%…105% and luminance within −1%…103%. It warns that gamut "legalisers" can create artefacts more visible than the gamut errors. **How:** clip with `lutyuv="y='clip(val,16,235)':u='clip(val,16,240)':v='clip(val,16,240)'"` only when a spec demands it (tested here 2026-10-24) [EBU R103-2000, https://tech.ebu.ch/docs/r/r103v1_1.pdf, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#lut_002c-lutrgb_002c-lutyuv, checked 2026-10-24]
849. **Out-of-gamut errors need area, not single pixels** — R103 recommends flagging an error only when it covers more than 1% of the active picture, after a ~1 MHz low-pass to ignore transient overshoots. **How:** use signalstats BRNG (fraction of out-of-range pixels) per frame and judge against ~1% (BRNG read 0.0135 on testsrc2, tested here 2026-10-24). [EBU R103-2000, https://tech.ebu.ch/docs/r/r103v1_1.pdf, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#signalstats, checked 2026-10-24]
850. **limiter filter** — limits pixel components to [min,max] per plane. `auto` uses the colourspace's signal levels for TV-range YUV. **How:** `ffmpeg -i in.mp4 -vf limiter=min=16:max=235:planes=1 -c:v libx264 out.mp4` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#limiter, checked 2026-10-24]

## Chroma subsampling, siting and planes

851. **J:a:b notation** — J = width of the reference region (usually 4), a = chroma samples in the first row, b = chroma changes between first and second row. **How:** yuv420p = 4:2:0, yuv422p = 4:2:2, yuv444p = 4:4:4 in ffmpeg names. [Wikipedia, https://en.wikipedia.org/wiki/Chroma_subsampling, checked 2026-10-24] [Encode Wiki, https://encode.wiki/reference/colorimetry/format, checked 2026-10-24]
852. **Bandwidth saving of subsampling** — Matrox: 4:2:2 cuts overall image bandwidth by 33%, 4:2:0 by 50%. **How:** expect 4:2:0 for all delivery and 4:2:2 for ProRes intermediates. [Matrox, https://video.matrox.com/en/media/guides-articles/introduction-color-spaces-video, checked 2026-10-24]
853. **Upsampling 4:2:0 to 4:4:4 recovers nothing** — it only makes the file bigger. 4:4:4 helps for screen recordings, game UI and text overlays, where thin coloured edges smear at 4:2:0. Most hardware decoders and browsers expect 4:2:0. **How:** keep the source subsampling, and use 4:4:4 only for text-heavy screen captures. [Encode Wiki, https://encode.wiki/reference/colorimetry/format, checked 2026-10-24]
854. **Pixel format says nothing about colour meaning** — a yuv420p10le file can be SDR BT.709, HDR10 or HLG. Primaries/transfer/matrix/range carry the meaning. **How:** never infer HDR from bit depth. Read `color_transfer`. [Encode Wiki, https://encode.wiki/reference/colorimetry/format, checked 2026-10-24]
855. **gbrp is planar RGB in G,B,R order** — ffmpeg's gbrp stores planes as G, B, R. gbrpf32le is planar 32-bit float. A wrong depth/order/endianness in a raw pipe gives garbage colours. **How:** grade in RGB with `format=gbrp,...,format=yuv420p` (tested here 2026-10-24 with curves) [Encode Wiki, https://encode.wiki/reference/colorimetry/format, checked 2026-10-24]
856. **Chroma location values** — AVChromaLocation: left = MPEG-2/4 4:2:0 and H.264 default. center = MPEG-1/JPEG. topleft = ITU-R 601, SMPTE 274M, MPEG-2 4:2:2. For HEVC BT.2020/BT.2100 (e.g. UHD Blu-ray) chroma is co-sited top-left. **How:** read `chroma_location` with ffprobe and keep it when re-encoding. [FFmpeg AVChromaLocation docs, https://ffmpeg-d.dpldocs.info/ffmpeg.libavutil.pixfmt.AVChromaLocation.html, checked 2026-10-24] [SDL docs, https://sdl-d.dpldocs.dlang.org/sdl.pixels.SDL_ChromaLocation.html, checked 2026-10-24]
857. **ITU guidance on ChromaLocType** — H-Suppl.19: typical SD/HD (NCG) uses ChromaLocType 0, WCG/UHD uses 2 (co-sited). x265 presets for BT.2100 use `--chromaloc 2`. **How:** for HDR HEVC add `chromaloc=2` in -x265-params when the source is co-sited. [ITU-T H Suppl.19, https://www.itu.int/epublications/publication/itu-t-h-suppl-19-2021-04-usage-of-video-signal-type-code-points, checked 2026-10-24] [x265 docs, https://x265.readthedocs.io/en/master/cli.html, checked 2026-10-24]
858. **Set or convert chroma siting** — the `-chroma_sample_location` codec option tags it. zscale `chromalin`/`chromal` converts. **How:** `ffmpeg -i in.mp4 -chroma_sample_location topleft -c:v libx264 out.mp4` and `ffmpeg -i in.mp4 -vf zscale=chromalin=left:chromal=topleft,format=yuv420p -c:v libx264 out.mp4` (both tested here 2026-10-24; ffprobe chroma_location=topleft) [ffmpeg codec docs, https://ffmpeg.org/ffmpeg-codecs.html#Codec-Options, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#zscale-1, checked 2026-10-24]
859. **Look at Y, U and V planes separately** — extractplanes splits components into greyscale streams, useful to see chroma noise or blocking. **How:** `ffmpeg -i in.mp4 -filter_complex "extractplanes=y+u+v[y][u][v]" -map "[y]" -frames:v 1 y.png -map "[u]" -frames:v 1 u.png -map "[v]" -frames:v 1 v.png` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#extractplanes, checked 2026-10-24]
860. **Shift misregistered chroma** — chromashift moves Cb/Cr horizontally/vertically (cbh, cbv, crh, crv; edge smear/warp). **How:** `ffmpeg -i in.mp4 -vf chromashift=cbh=2:crh=-2:edge=smear -c:v libx264 out.mp4` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#chromashift, checked 2026-10-24]
861. **Reduce chroma noise only** — chromanr averages chroma where the YUV difference is under `thres` (default 30) and leaves luma untouched. **How:** `ffmpeg -i in.mp4 -vf chromanr=thres=30:sizew=5:sizeh=5 -c:v libx264 out.mp4` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#chromanr, checked 2026-10-24]
862. **Swapped U/V or planes** — swapuv swaps U and V. shuffleplanes reorders planes (e.g. `0:2:1` swaps second and third). **How:** `-vf swapuv` or `-vf shuffleplanes=0:2:1` (both tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#swapuv, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#shuffleplanes, checked 2026-10-24]
863. **Detect RGB/BGR and YUV swaps with test sources** — rgbtestsrc should show red, green, blue stripes top to bottom. yuvtestsrc should show y, cb, cr stripes. **How:** `ffmpeg -f lavfi -i rgbtestsrc=size=320x240 -frames:v 1 rgb.png` then push it through your chain and compare (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#allrgb_002c-allyuv_002c-color_002c-colorchart_002c-colorspectrum_002c-haldclutsrc_002c-nullsrc_002c-pal75bars_002c-pal100bars_002c-rgbtestsrc_002c-smptebars_002c-smptehdbars_002c-testsrc_002c-testsrc2_002c-yuvtestsrc, checked 2026-10-24]
864. **Remove chroma to check luma alone** — lutyuv `u=128:v=128` turns video greyscale by neutralising chroma. **How:** `ffmpeg -i in.mp4 -vf "lutyuv=u=128:v=128" -c:v libx264 out.mp4` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#lut_002c-lutrgb_002c-lutyuv, checked 2026-10-24]

## Colour spaces and transfer functions (theory you need)

865. **Rec.709 primaries and white** — R 0.640/0.330, G 0.300/0.600, B 0.150/0.060, D65 white 0.3127/0.3290. sRGB uses the same primaries and white point. **How:** these are the `bt709` primaries in every ffmpeg option. [Encode Wiki, https://encode.wiki/reference/colorimetry/primaries, checked 2026-10-24] [Wikipedia, https://en.wikipedia.org/wiki/SRGB, checked 2026-10-24]
866. **BT.709 OETF formula** — V = 4.5·L for L < 0.018, else 1.099·L^0.45 − 0.099. **How:** an 18% grey gives V ≈ 0.409 (computed here with that formula, `python3 -c "print(1.099*0.18**0.45-0.099)"`, tested here 2026-10-24) [Wikipedia, https://en.wikipedia.org/wiki/Rec._709, checked 2026-10-24] [videomontazher, https://videomontazher.com/en/color-science/gamma-transfer, checked 2026-10-24]
867. **BT.709 never defined the display; BT.1886 does** — BT.1886 (2011) is the reference EOTF for SDR flat panels: L = a·max(V+b,0)^2.4, with a and b from screen white Lw and black Lb. It is used for Rec.709 and Rec.2020 SDR. **How:** grade SDR on a gamma 2.4 reference, and export tagged bt709. [Wikipedia, https://en.wikipedia.org/wiki/ITU-R_BT.1886, checked 2026-10-24] [Encode Wiki, https://encode.wiki/reference/colorimetry/transfer, checked 2026-10-24]
868. **OETF, EOTF, OOTF** — the camera applies an OETF (scene light → signal), the display an EOTF (signal → light), and the end-to-end relation is the OOTF. The two are not inverses because scene light differs from displayed light. "Gamma" is a loose word for these. **How:** always say which direction a curve or LUT goes. [Encode Wiki, https://encode.wiki/reference/colorimetry/transfer, checked 2026-10-24] [APSIPA Trans., https://www.emerald.com/atsip/article/7/1/1/1349743/The-technology-behind-the-exceptional-visual, checked 2026-10-24]
869. **Direction check: 0.5^2.4 vs 0.5^(1/2.4)** — 0.5 decoded with 2.4 gives ~0.189 and encoded gives ~0.749. Those are opposite directions of one pair, not two contrast presets. **How:** if a "gamma" fix makes things far too dark or light, you applied the inverse. [videomontazher, https://videomontazher.com/en/color-science/gamma-transfer, checked 2026-10-24]
870. **sRGB piecewise curve** — encode: 12.92·L (L ≤ 0.0031308) else 1.055·L^(1/2.4) − 0.055. Decode: V/12.92 (V ≤ 0.04045) else ((V+0.055)/1.055)^2.4. **How:** use these when converting sRGB PNG values to linear in Python. [Antler Post, https://antlerpost.com/colour-spaces/sRGB.html, checked 2026-10-24] [Microsoft MiniEngine, https://github.com/microsoft/DirectX-Graphics-Samples/blob/master/MiniEngine/Core/Shaders/ColorSpaceUtility.hlsli, checked 2026-10-24]
871. **sRGB EOTF: piecewise vs pure 2.2 is disputed** — the IEC text's reference display reads like pure 2.2, but Jack Holm (IEC secretary) says the piecewise function is the EOTF. ACES 2.0 ships both outputs. Many sRGB/Display P3 devices measure as pure 2.2. **How:** expect small shadow differences between monitors, and don't chase them in the grade. [Colour Science, https://www.colour-science.org/posts/srgb-eotf-pure-gamma-22-or-piece-wise-function/, checked 2026-10-24] [Antler Post, https://antlerpost.com/colour-spaces/sRGB.html, checked 2026-10-24]
872. **Rec.709 vs sRGB effective gamma** — both are piecewise. sRGB's decoding is close to 2.2 overall, while Rec.709's overall encoding gamma is about 0.5 (decoding ~2.0). **How:** an image made for sRGB web viewing and one graded on BT.1886 2.4 will not match exactly. [Image Engineering, https://image-engineering.de/library/technotes/714-color-spaces-rec-709-vs-srgb, checked 2026-10-24]
873. **Rec.2020 gamut** — primaries R 0.708/0.292, G 0.170/0.797, B 0.131/0.046 (D65). They lie on the spectral locus (630/532/467 nm). Coverage of CIE 1931: Rec.2020 75.8%, DCI-P3 53.6%, Rec.709 35.9%. **How:** `bt2020` primaries in zscale/setparams. [Wikipedia, https://en.wikipedia.org/wiki/Rec._2020, checked 2026-10-24] [ICC registry, https://registry.color.org/rgb-registry/bt2020, checked 2026-10-24]
874. **BT.2020 is a container, not the real gamut** — most HDR is graded on a P3-D65 monitor and delivered in BT.2020. Tag the stream bt2020 and record P3 in the mastering metadata, not smpte432. **How:** keep `colorprim=bt2020` with a P3 `master-display` string. [Encode Wiki, https://encode.wiki/reference/colorimetry/primaries, checked 2026-10-24]
875. **BT.2020 does not mean HDR** — UHD SDR also uses BT.2020 primaries. The transfer (smpte2084 or arib-std-b67) decides HDR. **How:** check `color_transfer`, not `color_primaries`. [Encode Wiki, https://encode.wiki/reference/colorimetry/primaries, checked 2026-10-24]
876. **P3 variants** — DCI-P3: 2.6 gamma, 48 cd/m², DCI white 0.314/0.351 (~6300 K, slightly green). P3-D65 keeps the primaries with D65 white. Apple Display P3 = P3 primaries + D65 + sRGB curve, tagged smpte432 + iec61966-2-1. **How:** never tag Display P3 phone stills as smpte431. [CinemaConfig, https://cinemaconfig.com/reference/dci-p3, checked 2026-10-24] [Encode Wiki, https://encode.wiki/reference/colorimetry/primaries, checked 2026-10-24] [ICC registry, https://registry.color.org/rgb-registry/dcip3, checked 2026-10-24]
877. **P3 cannot be fully carried in positive Rec.2020** — the P3 red lies very slightly outside the spectral locus, so 100% of P3 can't be encoded with positive Rec.2020 values. **How:** expect tiny red clipping in P3-limited masters in a 2020 container. [Antler Post, https://antlerpost.com/colour-spaces/P3D65.html, checked 2026-10-24]
878. **Retagging changes perceived saturation** — tagging BT.709 pixels as bt2020 makes colours oversaturated, and the reverse looks dull. Wide → narrow gamut is a real conversion. **How:** convert with explicit in/out primaries, e.g. `zscale=p=709:m=709:t=709:tin=2020_10,format=yuv420p` for BT.2020 SDR (tested here 2026-10-24) [Encode Wiki, https://encode.wiki/reference/colorimetry/primaries, checked 2026-10-24]
879. **colorspace filter is not an HDR tone mapper** — it converts matrix/primaries/trc, so use it for BT.2020 SDR → BT.709 SDR, not PQ/HLG → SDR. **How:** for HDR use the zscale+tonemap chain. [media-os skill, https://github.com/damionrashford/media-os/blob/main/skills/ffmpeg-hdr-color/SKILL.md, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#colorspace, checked 2026-10-24]
880. **CIE plot of your pixels** — ciescope overlays pixels on a CIE diagram with chosen gamut outlines (rec709, rec2020, dcip3 ...) and optional white point. **How:** `ffmpeg -i in.mp4 -vf "format=rgb24,ciescope=system=rec709:cie=xyy:gamuts=rec709+rec2020+dcip3:showwhite=1" -frames:v 1 -update 1 cie.png` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#ciescope, checked 2026-10-24]
881. **Scene-referred vs display-referred** — scene-referred signals represent light detected by the camera. Display-referred signals represent light on the grading monitor. They differ because the camera-to-display system is non-linear. **How:** log and HLG are scene-referred, PQ is display-referred: pick conversions accordingly. [BBC HDR FAQ, https://downloads.bbc.co.uk/rd/pubs/papers/HDR/BBC_HDRTV_FAQ.pdf, checked 2026-10-24]
882. **Relative vs absolute signals** — relative signals are ratios to the sensor peak (BT.601/709/2020, S-Log, LogC, HLG). An absolute signal gives each code a luminance in cd/m². PQ is the only absolute signal in wide use. **How:** a PQ code value means the same nits on every reference display. [BBC HDR FAQ, https://downloads.bbc.co.uk/rd/pubs/papers/HDR/BBC_HDRTV_FAQ.pdf, checked 2026-10-24]
883. **SDR is about 5 stops without banding** — BBC: 8-bit SDR TV has a displayed dynamic range of about 32:1 (5 stops) once banding is considered. A 10,000:1 HDR range needs about 700 just-noticeable levels, so 10-bit is necessary and 8 bits are inadequate. **How:** never deliver HDR in 8-bit. [BBC HDR FAQ, https://downloads.bbc.co.uk/rd/pubs/papers/HDR/BBC_HDRTV_FAQ.pdf, checked 2026-10-24]
884. **Wide-gamut tag pitfall on YouTube HDR** — YouTube: mastering in P3 and tagging Rec.2020 primaries gives an oversaturated look with shifted hues. DCI-P3 delivery is not supported, so grade in Rec.2020 with PQ or HLG. **How:** convert P3 to 2020 values before tagging bt2020. [YouTube Help, https://support.google.com/youtube/answer/7126552?hl=en, checked 2026-10-24]

## Bit depth, banding and precision

885. **10-bit gives four times the steps** — 8-bit = 256 levels per channel, 10-bit = 1024, 12-bit = 4096. A sky across 20 codes in 8-bit gets 80 in 10-bit. **How:** do heavy grades on a 10-bit intermediate. [mediacodec.dev, https://mediacodec.dev/wiki/bit-depth-and-banding/, checked 2026-10-24]
886. **Encode 10-bit even from 8-bit sources** — the encoder's prediction and quantisation keep more precision, so a 10-bit encode of an 8-bit source bands less at about the same bitrate. **How:** `ffmpeg -i in.mp4 -pix_fmt yuv420p10le -c:v libx264 -crf 18 out.mp4` (tested here 2026-10-24). Check the target player supports 10-bit H.264. [mediacodec.dev, https://mediacodec.dev/wiki/bit-depth-and-banding/, checked 2026-10-24]
887. **Dither hides steps but restores nothing** — dither spreads quantisation error into fine noise so contours are less visible. A dithered 8-bit image is still 8-bit. **How:** add dither only at the final bit-depth reduction (zscale `d=error_diffusion`). [Why It Looks Like That, https://whyitlookslikethat.com/articles/tv-bit-depth-8-bit-vs-10-bit-banding-hdr, checked 2026-10-24] [Versely, https://www.versely.studio/blog/ten-bit-intermediates-to-stop-grade-banding, checked 2026-10-24]
888. **zscale dither on the way down** — zscale `dither` takes none (default), ordered, random, error_diffusion. **How:** end an HDR→SDR chain with `zscale=t=709:m=709:r=limited:d=error_diffusion,format=yuv420p` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#zscale-1, checked 2026-10-24]
889. **8-bit PQ bands visibly** — PQ and HLG need at least 10-bit samples. `-pix_fmt yuv420p` on a 10-bit HDR source keeps the tags but quantises PQ to 8 bits. **How:** keep `yuv420p10le` for any HDR output. [Encode Wiki, https://encode.wiki/reference/colorimetry/transfer, checked 2026-10-24] [Encode Wiki, https://encode.wiki/guides/preserve-color-and-hdr, checked 2026-10-24]
890. **8-bit SDR inside HDR limits up-mapping** — BT.2408: up-mapping expands SDR highlights, and 8-bit resolution plus 8-bit compression limits how far before banding shows. **How:** prefer direct mapping of 8-bit phone clips into an HDR edit. [ITU-R BT.2408-7, https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2408-7-2023-PDF-E.pdf, checked 2026-10-24]
891. **10-bit is enough for HDR, 12-bit gives headroom** — BT.2408: good HDR programmes can be made with 10-bit infrastructure and codecs at bitrates like SDR. 12-bit production systems give more headroom for later processing of PQ and HLG. **How:** keep HDR masters at least `yuv420p10le`, and consider 12-bit when heavy processing follows. [ITU-R BT.2408-7, https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2408-7-2023-PDF-E.pdf, checked 2026-10-24]
892. **xvYCC uses the spare chroma codes** — xvYCC keeps BT.709 primaries/white and luma 16–235, and uses chroma codes 1–15 and 241–254 for extended-gamut colour. It is always limited range. **How:** a clipping legaliser on chroma 16–240 throws such colours away, so don't clip camera files tagged xvYCC (`color_transfer=iec61966-2-4`). [Wikipedia, https://en.wikipedia.org/wiki/XvYCC, checked 2026-10-24] [Encode Wiki, https://encode.wiki/reference/colorimetry/transfer, checked 2026-10-24]
893. **Float RGB for precision** — tonemap expects single-precision float. gbrpf32le carries out-of-range values between filters. **How:** `ffmpeg -i in.mp4 -vf "format=gbrpf32le,exposure=exposure=0.3,format=yuv420p" -c:v libx264 out.mp4` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#tonemap, checked 2026-10-24] [Encode Wiki, https://encode.wiki/reference/colorimetry/format, checked 2026-10-24]

## Scopes in ffmpeg

894. **Waveform with legal-range graticule in IRE** — waveform `graticule=green|orange|invert` draws legal broadcast ranges. `scale=digital|millivolts|ire` sets the units. **How:** `ffmpeg -i in.mp4 -vf "waveform=graticule=green:scale=ire:flags=numbers" -frames:v 1 -update 1 wf.png` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#waveform, checked 2026-10-24]
895. **Waveform in millivolts** — `scale=millivolts` for engineers who think in mV (PAL 100 IRE = 700 mV). **How:** `-vf "waveform=graticule=orange:scale=millivolts"` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#waveform, checked 2026-10-24] [Wikipedia IRE, https://en.wikipedia.org/wiki/IRE_(unit), checked 2026-10-24]
896. **Peak envelope over a whole clip** — waveform/vectorscope `envelope=peak` holds min and max values over time, so out-of-range values show without watching every frame. **How:** `-vf "waveform=envelope=peak:graticule=green"` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#waveform, checked 2026-10-24]
897. **Overlay RGB waveform for neutrals** — `display=overlay` superimposes the component graphs, which makes it easier to see if whites, greys and blacks that should be identical line up. **How:** `-vf "format=gbrp,waveform=display=overlay:components=7"` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#waveform, checked 2026-10-24]
898. **Waveform filters: flat, aflat, chroma** — `filter=flat` shows luma and chroma combined, `aflat` the Cb–Cr difference, `chroma` only chroma, `color` the actual colour values. **How:** `-vf "waveform=filter=chroma:components=7"` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#waveform, checked 2026-10-24]
899. **Vectorscope with named targets and white point** — vectorscope `graticule=color` with `flags=name+white` draws colour point names and the white target. `colorspace=601|709` picks the graticule. **How:** `-vf "vectorscope=mode=color4:envelope=peak:graticule=color:flags=name+white:colorspace=709"` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#vectorscope, checked 2026-10-24]
900. **Vectorscope of shadows or highlights only** — `lthreshold`/`hthreshold` ignore pixels whose third component (luma) is outside the band (fractions of max), so you can see the cast of shadows and highlights separately. **How:** shadows `-vf "vectorscope=mode=color3:lthreshold=0:hthreshold=0.3"`, highlights `lthreshold=0.7:hthreshold=1` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#vectorscope, checked 2026-10-24]
901. **Histogram parade, logarithmic** — histogram `display_mode=parade` puts components side by side, and `levels_mode=logarithmic` shows sparse values. **How:** `-vf "histogram=display_mode=parade:levels_mode=logarithmic"` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#histogram, checked 2026-10-24]
902. **Histogram across time** — thistogram keeps past histograms, so exposure drift or flicker over a shot shows as one picture. **How:** `ffmpeg -i in.mp4 -vf "thistogram=display_mode=overlay:envelope=1:slide=picture" -update 1 th.png` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#thistogram, checked 2026-10-24]
903. **Read exact pixel numbers** — datascope prints pixel values (hex or dec) for a region. pixscope shows sample values plus area statistics (minimum input 640x480). **How:** `-vf "datascope=s=640x360:x=300:y=150:mode=color2:format=dec:axis=1"` and `-vf "scale=640:480,pixscope=x=0.5:y=0.5:w=7:h=7"` (both tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#datascope, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#pixscope, checked 2026-10-24]
904. **signalstats percentiles and colour metrics** — YLOW/YHIGH are the 10th/90th percentile luma. SATAVG/SATMAX are saturation, HUEMED/HUEAVG are hue, and Y/U/VBITDEPTH the plane depth. These are steadier than min/max. **How:** `ffmpeg -i in.mp4 -vf "signalstats,metadata=mode=print:file=ss.txt" -frames:v 1 -f null -` then grep YLOW/YHIGH (tested here 2026-10-24: YLOW 41, YHIGH 210 on testsrc2) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#signalstats, checked 2026-10-24]
905. **Highlight out-of-broadcast-range pixels** — `signalstats=out=brng:color=red` paints illegal pixels. `stat=brng` adds a BRNG value per frame. **How:** `ffmpeg -i in.mp4 -vf "signalstats=out=brng:color=red" -frames:v 1 -update 1 brng.png` and `-vf "signalstats=stat=brng,metadata=mode=print:key=lavfi.signalstats.BRNG:file=brng.txt"` (both tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#signalstats, checked 2026-10-24]
906. **One QC sheet: picture + waveform + vectorscope** — Tek describes the waveform for luma/legal levels and the vectorscope for chroma. Stack them under the frame. **How:** `ffmpeg -i in.mp4 -filter_complex "[0:v]split=3[a][b][c];[b]waveform=graticule=green:scale=ire,scale=640:360[w];[c]format=yuv444p,vectorscope=mode=color3:graticule=color,scale=360:360,pad=640:360[v];[a][w]vstack[top];[top][v]vstack" -frames:v 1 -update 1 panel.png` (tested here 2026-10-24) [Tektronix, https://download.tek.com/document/25W_29166_0_Interactive.pdf, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#waveform, checked 2026-10-24]
907. **Legal luma on a waveform** — the brightest luma should not go past 100%, with occasional speculars allowed to about 105% depending on the broadcaster, and the darkest not below 0%. No digital format uses 7.5 IRE setup. **How:** read the IRE waveform from 894 against 0/100. [Tektronix, https://download.tek.com/document/25W_29166_0_Interactive.pdf, checked 2026-10-24]
908. **IRE, millivolts, code values** — 100 IRE = 714 mV in NTSC, and PAL peaks at 700 mV. A code value, its full-range percentage and its legal-range IRE are three different numbers (code 95 = 9.29% full range = 3.5 IRE legal). **How:** say which scale you mean, and use `waveform=scale=ire` for IRE. [Wikipedia IRE, https://en.wikipedia.org/wiki/IRE_(unit), checked 2026-10-24] [Leumos, https://leumos.ai/tools/log-reference, checked 2026-10-24]
909. **75% vs 100% bar targets** — if 75% bars fall short of targets the scope is set for 100% bars, and vice versa. In SMPTE bars only the top two-thirds (75% bars) hit the standard targets. **How:** generate bars and check the chain: `ffmpeg -f lavfi -i smptehdbars=size=1280x720 -vf "format=yuv444p,vectorscope=mode=color3:graticule=color:flags=name" -frames:v 1 bars_vs.png` (tested here 2026-10-24) [Tektronix FAQ, https://www.tek.com/en/support/faqs/why-are-my-color-bars-not-hitting-vectorscope-targets, checked 2026-10-24] [Wikipedia, https://en.wikipedia.org/wiki/SMPTE_color_bars, checked 2026-10-24]
910. **Test patterns ffmpeg can make** — smptehdbars (SMPTE RP 219), pal75bars/pal100bars (EBU 75%/100%), colorchart (colour checker, presets reference or skintones), colorspectrum, allrgb/allyuv (4096x4096 every colour), haldclutsrc. **How:** `ffmpeg -f lavfi -i colorchart=preset=skintones -frames:v 1 skin.png` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#allrgb_002c-allyuv_002c-color_002c-colorchart_002c-colorspectrum_002c-haldclutsrc_002c-nullsrc_002c-pal75bars_002c-pal100bars_002c-rgbtestsrc_002c-smptebars_002c-smptehdbars_002c-testsrc_002c-testsrc2_002c-yuvtestsrc, checked 2026-10-24]
911. **Pseudocolor presets for false colour** — pseudocolor has built-in LUTs incl. range1, range2, shadows, highlights, solar, nominal, preferred, total, heat, viridis. **How:** `ffmpeg -i in.mp4 -vf pseudocolor=preset=preferred -frames:v 1 -update 1 fc.png` (tested here 2026-10-24). The docs don't publish the band levels, so use it to spot regions, not to read IRE. [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#pseudocolor, checked 2026-10-24]
912. **Paint only too-bright luma** — the pseudocolor docs give an expression that turns luma above ymax into a gradient and leaves the rest. **How:** `-vf "pseudocolor='if(between(val,ymax,amax),lerp(ymin,ymax,(val-ymax)/(amax-ymax)),-1):if(between(val,ymax,amax),lerp(umax,umin,(val-ymax)/(amax-ymax)),-1):if(between(val,ymax,amax),lerp(vmin,vmax,(val-ymax)/(amax-ymax)),-1)'"` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#pseudocolor, checked 2026-10-24]
913. **ARRI false-colour zones** — ARRI ALEXA false colour: purple 0–2.5% black clipping, blue 2.5–4% just above black, green 38–42% = 18% grey, pink 52–56% = one stop over grey, yellow 97–99% just below clipping, red 99–100% clipping. **How:** read the matching IRE bands off `waveform=scale=ire` when no false colour monitor is around. [ARRI ALEXA manual, https://www.manualslib.com/manual/1152031/Arri-Alexa.html?page=37, checked 2026-10-24] [ARRI DR whitepaper, https://arri.com/resource/blob/295460/e10ff8a5b3abf26c33f8754379b57442/2022-09-28-arri-dynamic-range-whitepaper-data.pdf, checked 2026-10-24]

## Exposure, middle grey and reference cards

914. **Zebras warn, they don't expose** — Sony: zebra stripes show areas near overexposure at a set IRE (70–100). They are not recorded and do not control exposure. **How:** in post, use 905 (brng) or 912 for the same warning. [Sony, https://www.sony.com/electronics/support/articles/00077788, checked 2026-10-24]
915. **70 IRE zebra on skin highlights** — set zebra to 70 IRE and close the iris until only a stripe or two remain on a cheekbone or forehead. One trainer puts Caucasian skin highlights around 80 IRE, another "skin falls nicely between 75/85 IRE". **How:** check face highlights on the IRE waveform near those values, don't force them. [Pieter de Vries, https://pieterdevries.com.au/2021/06/25/how-to-set-the-correct-exposure-using-zebra/, checked 2026-10-24] [Micro Documentary Filmmaker, https://microdocfilmmaker.wordpress.com/2009/01/17/using-zebra-stripes-for-proper-exposure/, checked 2026-10-24]
916. **Kodak grey card procedure** — 18% grey with 3% black and 90% white patches. Shoot it before every major lighting setup to give post exposure and colour balance references. It reflects R, G, B equally. **How:** crop the card in post and read its numbers (918). [Kodak, https://www.kodak.com/en/motion/page/gray-card/, checked 2026-10-24]
917. **Grey cards must be spectrally flat** — a grey card's flat reflectance spectrum keeps it the colour of its illuminant (no metamerism). DSC warns look-alike cards with a yellow cast give blue-biased images when normalised. **How:** trust only proper cards as neutral references. [Wikipedia, https://en.wikipedia.org/wiki/Gray_card, checked 2026-10-24] [SMPTE / DSC Labs, https://www.smpte.org/dsc-smpte-charts, checked 2026-10-24]
918. **Measure a card or neutral patch in ffmpeg** — crop the patch and read YAVG/UAVG/VAVG. A neutral patch reads U and V at 128 (8-bit). **How:** `ffmpeg -i in.mp4 -vf "crop=40:40:300:160,signalstats,metadata=mode=print:file=patch.txt" -frames:v 1 -f null -` (tested here 2026-10-24: grey testsrc2 patch gave U 128, V 128) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#signalstats, checked 2026-10-24] [Encode Wiki, https://encode.wiki/reference/colorimetry/range, checked 2026-10-24]
919. **18% grey ≈ 41% in Rec.709** — the Rec.709 OETF puts 18% grey at about 40.9% (video levels). DSC places 18% grey "usually around 40 IRE", and some DPs peg 45–50%. It is a choice. **How:** read the card on `waveform=scale=ire` and expect roughly 40–50% depending on the chosen placement. [xtremestuff, https://xtremestuff.net/recording-editing-with-hybrid-log-gamma-part-1/, checked 2026-10-24] [SMPTE / DSC Labs, https://www.smpte.org/dsc-smpte-charts, checked 2026-10-24] [cinematography.net, https://www.cinematography.net/edited-pages/18GreyTranslationToIREValue.htm, checked 2026-10-24]
920. **Middle grey per log curve** — colourist values for 18% grey: ARRI LogC3 .391, LogC4 .28, BMD Film Gen5 .466, Canon Log 2 .398, Canon Log 3 .343, DJI D-Log .399, RED Log3G10 .333, Panasonic V-Log .423, Sony S-Log3 .411. **How:** check a grey card on log footage at these levels before converting. [Jamie Neale, https://www.jamiegrades.com/blog/midgrey, checked 2026-10-24]
921. **V-Log anatomy** — V-Log maps 0% reflectance to 7.3% IRE, 18% to 42% and 90% to 61%, with ~5.5 stops above 100% IRE. Below 18% it behaves like Rec.709. **How:** a lifted black around 7% is normal on V-Log, so don't "fix" it before conversion. [Interceptor121, https://interceptor121.com/2021/02/07/the-truth-about-v-log/, checked 2026-10-24]
922. **Don't mix IRE tables between makers** — Sony and Panasonic print legal-range IRE beside code values, while ARRI's LogC4 IRE column is full-range percent. S-Log3 grey is 10-bit code 420 = 41.06% full = 40.64% legal. **How:** convert codes yourself: legal% = (CV−64)/876. [Leumos, https://leumos.ai/tools/log-reference, checked 2026-10-24]
923. **Stops are doublings of linear light** — one stop up doubles linear light, so grey 0.18 becomes 0.36, then 0.72. **How:** the ffmpeg `exposure` filter takes EV in −3…+3 (`exposure=exposure=0.5:black=0`, tested here 2026-10-24) [Wikipedia, https://en.wikipedia.org/wiki/Exposure_value, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#exposure, checked 2026-10-24]
924. **Remove exposure flicker** — deflicker smooths frame luminance variations with a moving average (size 2–129, modes am/gm/hm/qm/cm/pm/median). **How:** `ffmpeg -i in.mp4 -vf deflicker=size=5:mode=pm -c:v libx264 out.mp4` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#deflicker, checked 2026-10-24]
925. **Histogram equalisation only for degraded video** — histeq is an automatic contrast filter meant only for degraded or poorly captured video. Limit `intensity` to avoid wash-out, and `antibanding` adds slight random variation. **How:** `-vf histeq=strength=0.2:intensity=0.21:antibanding=weak` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#histeq, checked 2026-10-24]
926. **Auto levels with normalize** — normalize stretches each channel's range to black..white. `smoothing` (frames) acts like camera auto-exposure to stop flicker. `independence=0` keeps hue, `1` removes casts. `strength` blends. **How:** `-vf normalize=blackpt=black:whitept=white:smoothing=50:independence=0:strength=0.5` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#normalize, checked 2026-10-24]
927. **BT.2408 HDR line-up levels** — 18% grey card: 26 cd/m², 38% PQ, 38% HLG. Greyscale chart 90%: 179 cd/m², 57% PQ, 73% HLG. HDR Reference White (100%, also Graphics White): 203 cd/m², 58% PQ, 75% HLG (PQ display, or a 1000 cd/m² HLG display). **How:** put a 58% PQ / 75% HLG marker on your HDR waveform. [ITU-R BT.2408-7, https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2408-7-2023-PDF-E.pdf, checked 2026-10-24]
928. **BT.2408 skin and grass ranges in HDR** — Fitzpatrick 1–2 skin: 65–110 cd/m², 45–55% PQ, 55–65% HLG. Types 3–4: 40–85, 40–50% PQ, 45–60% HLG. Types 5–6: 10–40, 30–40% PQ, 25–45% HLG. Grass: 30–65, 40–45% PQ, 40–55% HLG. **How:** check face levels on PQ/HLG grades against these. [ITU-R BT.2408-7, https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2408-7-2023-PDF-E.pdf, checked 2026-10-24]
929. **Grey cards drift after grading** — BT.2408: 18% grey is closest to skin and good for matching SDR/HDR cameras (not affected by an SDR knee), but artistic painting/grading moves it, so its level varies after looks are applied. **How:** use the grey card for technical matching before the look. [ITU-R BT.2408-7, https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2408-7-2023-PDF-E.pdf, checked 2026-10-24]
930. **Comfortable HDR brightness** — NHK test: images whose average luminance was under 25% of display peak were not judged too bright. BBC: mean display luminance 5–80 cd/m² gave nearly no annoying brightness jumps, and up to 160 cd/m² is an extended creative range. **How:** keep scene averages of HDR edits inside that band, and watch cuts between bright and dark shots. [ITU-R BT.2408-7, https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2408-7-2023-PDF-E.pdf, checked 2026-10-24]

## White balance and colour temperature

931. **Grey world needs linear light** — the grayworld filter corrects colour on the grey-world assumption and works in linear light, so linearise first. **How:** `ffmpeg -i in.mp4 -vf zscale=transfer=linear,grayworld,zscale=transfer=bt709,format=yuv420p -c:v libx264 out.mp4` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#grayworld, checked 2026-10-24]
932. **Grey edge / max edge illuminant estimate** — greyedge estimates the illuminant from edges. The docs' Grey Edge example is `difford=1:minknorm=5:sigma=2`, and Max Edge is `minknorm=0`. **How:** `ffmpeg -i in.mp4 -vf greyedge=difford=1:minknorm=5:sigma=2 -c:v libx264 out.mp4` (tested here 2026-10-24; max edge also ran) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#greyedge, checked 2026-10-24]
933. **Auto white balance per frame with colorcorrect** — colorcorrect (YUV) with `analyze=average|minmax|median` derives shadow/highlight balance each frame. `manual` uses rl/bl/rh/bh. **How:** `-vf colorcorrect=analyze=median` (tested here 2026-10-24; YAVG/UAVG/VAVG moved slightly on testsrc2) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#colorcorrect, checked 2026-10-24]
934. **Manual black/white spot balance** — colorcorrect rl/bl set the red/blue shadow spot, rh/bh the highlight spot (−1…1), plus a saturation control (−3…3). **How:** `-vf colorcorrect=rl=-0.05:bl=0.05:rh=0.03:bh=-0.03:saturation=1` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#colorcorrect, checked 2026-10-24]
935. **Independent normalize removes casts** — normalize with `independence=1` (default) stretches channels separately, which shifts colour and can remove casts. `0` links them and preserves hue. **How:** `-vf normalize=blackpt=black:whitept=white:smoothing=50:independence=1` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#normalize, checked 2026-10-24]
936. **Gray vs white card for camera WB** — Art Adams got better results white balancing from grey cards. He found the Canon 5D balanced better off a grey card than a white card, and he exposes white and grey references to about the same IRE. X-Rite says the 18% card is for exposure and a WB card for colour. **How:** if both exist in a shot, sample the grey one for 931. [ProVideo Coalition, https://www.provideocoalition.com/secret-art-of-white-balancing/, checked 2026-10-24] [X-Rite, https://www.xrite.com/service-support/18graycardversesawhitebalancecard, checked 2026-10-24]
937. **Mireds measure temperature shifts** — mired = 1,000,000 / K. Equal mired steps are closer to equal perceived differences than equal kelvin steps. A 5700 K → 3200 K correction is about −137 mireds (CTB). Negative-mired gels look blue/green, positive amber/red. **How:** `python3 -c "print(round(1e6/5700-1e6/3200))"` → −137 (tested here 2026-10-24) [Wikipedia, https://en.wikipedia.org/wiki/Mired, checked 2026-10-24]
938. **Metameric failure under peaky lights** — two materials can match under one light and not another. Most fluorescent lights have peaky spectra, so matches made under them may fail elsewhere. **How:** a mixed-light shot may not balance with one global correction, so use a secondary (qualifier/window section). [Wikipedia, https://en.wikipedia.org/wiki/Metamerism_(color), checked 2026-10-24]
939. **ColorChecker as a target** — the 24-patch chart has six greys, six primaries/secondaries and natural colours (dark/light skin, blue sky, foliage), with reflectances that mimic natural objects. Pigments changed in Nov 2014, so old RGB tables don't fit new cards. **How:** generate a reference chart with `colorchart=preset=reference` (tested here 2026-10-24) [Wikipedia, https://en.wikipedia.org/wiki/ColorChecker, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#allrgb_002c-allyuv_002c-color_002c-colorchart_002c-colorspectrum_002c-haldclutsrc_002c-nullsrc_002c-pal75bars_002c-pal100bars_002c-rgbtestsrc_002c-smptebars_002c-smptehdbars_002c-testsrc_002c-testsrc2_002c-yuvtestsrc, checked 2026-10-24]

## Primary correction tools in ffmpeg

940. **Lift, gamma, gain, offset** — Resolve: Lift targets shadows, Gamma midtones, Gain highlights, Offset affects the image uniformly. The master sliders under each wheel control YRGB of that range. Ranges overlap widely. **How:** ffmpeg filters whose docs describe the matching controls: `colorlevels` input black/white points, `lutyuv=y=gammaval(g)` for gamma, `colorbalance` for shadows/midtones/highlights colour. [Blackmagic Colorist Guide 20, https://documents.blackmagicdesign.com/UserManuals/DaVinci-Resolve-20-Colorist-Guide.pdf, checked 2026-10-24] [Blackmagic, https://www.blackmagicdesign.com/products/davinciresolve/color, checked 2026-10-24]
941. **Log wheels are for log data** — Resolve's Log mode gives Shadow/Midtone/Highlight/Offset with narrower, adjustable ranges meant for log-encoded images. Offset/Printer Points adjust the signal in a linear, film-oriented way. **How:** when grading log in ffmpeg before conversion, prefer offset-style moves (colorlevels output levels) over gamma. [DaVinci Resolve 21 manual ch.131, https://docs.imaster.org/davinci-resolve-21-manual/part-10-color/ch.-131-primaries-palette, checked 2026-10-24]
942. **ASC CDL math** — out = (in × slope + offset)^power per R, G, B, plus one saturation number (v1.2). Slope ≥ 0 (nominal 1), offset any (0), power > 0 (1). **How:** bake a CDL into a cube with Python (identity loops, apply the formula) and use `lut3d=file=cdl.cube` (tested here 2026-10-24) [Wikipedia, https://en.wikipedia.org/wiki/ASC_CDL, checked 2026-10-24]
943. **CDL values only mean something in a known space** — ACESCentral: CDL parameters in ACES workflows are meaningful when made and read on ACEScc values. Wikipedia: calibrations, viewing devices and output transforms must match at both ends. **How:** send a CDL only with a note of the space it was made in. [ACESCentral, https://acescentral.com/knowledge-base-2/aces-working-spaces/, checked 2026-10-24] [Wikipedia, https://en.wikipedia.org/wiki/ASC_CDL, checked 2026-10-24]
944. **Levels with colour preservation** — colorlevels has `preserve=lum|max|avg|sum|nrm|pwr` so a levels move doesn't shift colour. **How:** `-vf colorlevels=rimin=0.039:gimin=0.039:bimin=0.039:rimax=0.96:gimax=0.96:bimax=0.96:preserve=lum` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#colorlevels, checked 2026-10-24]
945. **Output levels to constrain range** — colorlevels romin/romax (0–1) pick a constrained output range. The docs' "increase brightness" example is `romin=0.5:gomin=0.5:bomin=0.5`. **How:** `-vf colorlevels=romin=0.05:gomin=0.05:bomin=0.05:romax=0.95:gomax=0.95:bomax=0.95` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#colorlevels, checked 2026-10-24]
946. **Monotonic curves avoid overshoot** — curves uses natural cubic splines by default. `interp=pchip` guarantees monotonic transitions between points (no wiggle past a point). **How:** `-vf "curves=interp=pchip:master='0/0 0.25/0.20 0.75/0.80 1/1'"` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#curves, checked 2026-10-24]
947. **Master curve is a second pass** — curves `master` is applied after r/g/b like a post LUT. `all` sets r, g and b together. **How:** `-vf "curves=all='0/0.05 1/0.95'"` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#curves, checked 2026-10-24]
948. **Per-channel curve for a mid-tone cast** — the docs' example lifts the blue midtone slightly with `curves=blue='0/0 0.5/0.58 1/1'`. **How:** use a per-channel mid point for a cast that sits only in the mids (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#curves, checked 2026-10-24]
949. **Gamma on luma only** — lutyuv `gammaval(g)` applies a power to luma between minval and maxval. **How:** `-vf "lutyuv=y=gammaval(0.8)"` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#lut_002c-lutrgb_002c-lutyuv, checked 2026-10-24]
950. **Colour contrast between opposing pairs** — colorcontrast sets red-cyan, green-magenta and blue-yellow contrast. Each needs a weight (`rcw` etc.) above 0, and `pl` preserves lightness. **How:** `-vf colorcontrast=rc=0.2:rcw=0.5:pl=0.5` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#colorcontrast, checked 2026-10-24]
951. **Channel mixer with luminance preserved** — colorchannelmixer `pc=lum|max|avg|sum|nrm|pwr` with amount `pa` keeps brightness while channels are remixed. **How:** `-vf colorchannelmixer=rr=1.1:bb=0.9:pc=lum:pa=1` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#colorchannelmixer, checked 2026-10-24]
952. **vibrance filter options** — intensity −2…2 (boost or alter), per-channel balance rbal/gbal/bbal, luma coefficients, and `alternate` (with negative intensity: shift colours instead of greying). **How:** `-vf vibrance=intensity=0.3` and `-vf vibrance=intensity=-0.5:alternate=0` (both tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#vibrance, checked 2026-10-24]
953. **Saturation and contrast interact** — Resolve's colorist guide puts balance first, and the Frame.io guide orders luma → chroma balance → saturation. Set luma before judging saturation. **How:** order the ffmpeg chain levels/curves → balance → `eq=saturation`. [Frame.io Workflow Guide, https://workflow.frame.io/guide/primary-color-correction, checked 2026-10-24] [Blackmagic, https://www.blackmagicdesign.com/products/davinciresolve/color, checked 2026-10-24]
954. **Generic lut/lutrgb expressions** — lutrgb/lutyuv compute a table from expressions using val, clipval, maxval, minval, negval, clip(), gammaval(). **How:** `-vf "format=gbrp,lutrgb=r='pow(clip((val/maxval)*1.05,0,1),1.0)*maxval',format=yuv420p"` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#lut_002c-lutrgb_002c-lutyuv, checked 2026-10-24]
955. **Selective colour by purity** — selectivecolor adjusts CMYK per colour range (reds, yellows, greens, cyans, blues, magentas, whites, neutrals, blacks). `correction_method=relative|absolute` (default absolute). It reads Photoshop .asv files. **How:** `-vf "selectivecolor=correction_method=relative:greens=.5 0 -.33 0:blues=0 .27"` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#selectivecolor, checked 2026-10-24]
956. **Hue-vs curves as ffmpeg moves** — Resolve's Hue vs Hue changes one hue to another (e.g. a too-cyan sky to blue), Hue vs Sat and Hue vs Lum change saturation/lightness of a hue. **How:** nearest ffmpeg tool is `huesaturation=hue=-10:colors=c+b:strength=1:lightness=1` (lightness=1 keeps lightness) (tested here 2026-10-24) [Blackmagic, https://www.blackmagicdesign.com/products/davinciresolve/color, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#huesaturation, checked 2026-10-24]
957. **Keep one colour, grey the rest** — colorhold (RGB) and hsvhold (HSV) turn everything except a chosen colour range grey, with similarity and blend. **How:** `-vf colorhold=color=red:similarity=0.3:blend=0.1` and `-vf hsvhold=hue=0:sat=0.7:val=0.5:similarity=0.3:blend=0.1` (both tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#colorhold, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#hsvhold, checked 2026-10-24]

## LUTs: 1D, 3D, Hald

958. **1D vs 3D LUT** — a 1D LUT is three independent curves (no cross-channel effects). A 3D LUT is indexed by R, G and B together and can represent any colour transform. **How:** use `lut1d` for pure tone/gamma, `lut3d` for colour. [AgX docs, https://zhjngli.github.io/AgX/reference/concepts/lut-format.html, checked 2026-10-24]
959. **Apply a 1D .cube** — lut1d reads cube and csp 1D files with nearest/linear/cosine/cubic/spline interpolation. **How:** write `LUT_1D_SIZE 1024` + 1024 lines of "v v v", then `ffmpeg -i in.mp4 -vf lut1d=file=g.cube:interp=cubic -c:v libx264 out.mp4` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#lut1d, checked 2026-10-24]
960. **lut3d file formats** — 3dl (After Effects), cube (Iridas), dat (DaVinci), m3d (Pandora), csp (cineSpace). Interpolation nearest, trilinear, tetrahedral (default), pyramid, prism. **How:** `ffmpeg -hide_banner -h filter=lut3d` shows the default (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#lut3d-1, checked 2026-10-24]
961. **.cube layout** — optional TITLE, `LUT_3D_SIZE N` or `LUT_1D_SIZE N`, optional DOMAIN_MIN/MAX, then N³ RGB lines with red changing fastest. **How:** an identity 33-cube written with red in the innermost loop gave 88 dB PSNR through lut3d on a PNG, while blue-fastest gave 3.7 dB (tested here 2026-10-24). One site claims blue fastest, and the test shows that is wrong for ffmpeg. [LUTLINE, https://lutline.app/learn/cube-lut-format/, checked 2026-10-24]
962. **LUT sizes and file weight** — 17³ = 4,913 lines (~120 KB), 33³ = 35,937 (~900 KB), 65³ = 274,625 (~7 MB). Creative looks are usually 25 or 33, while camera conversion tables are often 65 so log shadows don't band. **How:** export conversions at 65 and looks at 33. [LUTLINE, https://lutline.app/learn/cube-lut-format/, checked 2026-10-24] [Canon UK, https://www.canon.co.uk/pro/stories/how-to-use-3d-luts/, checked 2026-10-24]
963. **Tetrahedral beats trilinear per grid point** — SMPTE review (BT.2100 PQ): tetrahedral interpolation outperformed others for SDR and HDR, matching trilinear quality with a LUT 20–25% smaller. For 10-bit SDR, >41³ trilinear or >31³ tetrahedral avoids artefacts. **How:** keep lut3d's default tetrahedral. [SMPTE MIJ / DOI, https://doi.org/10.5594/jmi.2020.2965022, checked 2026-10-24]
964. **Camera Look File LUT rules (Canon)** — Canon Look Files must be 17 or 33 grid .cube, built for full-range in and out. **How:** export 33-point full-range cubes for on-camera use. [Canon UK, https://www.canon.co.uk/pro/stories/how-to-use-3d-luts/, checked 2026-10-24]
965. **Test a LUT pipeline with an identity cube** — an identity LUT must change nothing, which proves the order and range handling. **How:** Python writes a 33³ identity (`for b: for g: for r:`), then `ffmpeg -i frame.png -vf lut3d=file=id33.cube:interp=tetrahedral -frames:v 1 out.png` and `ffmpeg -i frame.png -i out.png -lavfi psnr -f null -` (tested here 2026-10-24: 88 dB) [LUTLINE, https://lutline.app/learn/cube-lut-format/, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#psnr, checked 2026-10-24]
966. **Hald CLUT geometry** — a Hald of level N is an N³×N³ pixel image holding an (N²)³ cube, e.g. level 8 = 512×512 = 64³. Square-image rules mean 17/33/65 cubes can't be written as Hald. **How:** `ffmpeg -f lavfi -i haldclutsrc=8 -frames:v 1 hald.png` (tested here 2026-10-24) [RawCut, https://www.rawcut.art/tools/hald-clut, checked 2026-10-24] [GraphicsMagick, http://www.graphicsmagick.org/api/hclut.html, checked 2026-10-24]
967. **Bake any ffmpeg global grade into a LUT** — run the identity Hald through the colour filters, then apply it with haldclut. Only global colour operations survive (no sharpening, denoise or local effects). **How:** `ffmpeg -f lavfi -i haldclutsrc=8 -vf "curves=preset=increase_contrast,colortemperature=temperature=5500" -frames:v 1 hald.png` then `ffmpeg -i in.mp4 -i hald.png -filter_complex "[0][1]haldclut" out.mp4` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#haldclut-1, checked 2026-10-24] [RawPedia, https://rawpedia.rawtherapee.com/Film_Simulation, checked 2026-10-24]
968. **Convert a Hald PNG to .cube** — the identity Hald holds every cube entry once in known order, so its pixels read row by row are the cube entries. **How:** Python/PIL: read hald.png pixels in order, write `LUT_3D_SIZE 64` and each pixel/255 as a line, then `lut3d=file=hald64.cube` (tested here 2026-10-24: 43.6 dB PSNR vs the haldclut result) [RawCut, https://www.rawcut.art/tools/hald-clut, checked 2026-10-24]
969. **Animated CLUTs** — haldclut accepts a video stream as the CLUT (`clut=all` default, `repeatlast=1` keeps the last one), so a grade can change over time. **How:** `ffmpeg -f lavfi -i haldclutsrc=8 -vf "hue=H=2*PI*t:s=sin(2*PI*t)+1, curves=cross_process" -t 2 -c:v ffv1 clut.nut` then `-filter_complex "[0][1]haldclut"` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#haldclut-1, checked 2026-10-24]
970. **YouTube SDR down-conversion hint LUT** — YouTube's HDR metadata tool can pack a .cube (Rec.2020 PQ → Rec.709 gamma 2.4, plus your primaries/curves/keys) as a hint for its automatic SDR version. Windows, blur keys and per-shot changes don't work. **How:** make one global LUT for the whole HDR video and give it to the tool. [YouTube Help, https://support.google.com/youtube/answer/7126552?hl=en, checked 2026-10-24]

## Secondaries: qualifiers, windows, masks (ffmpeg way)

971. **Primary vs secondary** — Frame.io: a primary correction changes every pixel. Resolve: a secondary isolates part of the image with a key (white = change, black = leave), from a qualifier, a Power Window or an external matte. **How:** in ffmpeg the key is the third input of `maskedmerge`. [Frame.io Workflow Guide, https://workflow.frame.io/guide/primary-color-correction, checked 2026-10-24] [DaVinci Resolve 11 manual, https://ltbits.github.io/davinci-resolve-manuals/DR11/DR11-RM-12.pdf, checked 2026-10-24]
972. **maskedmerge semantics** — mask value 0 keeps the first input, maximum (255) takes the second, in-between mixes, per plane. **How:** put mask, original and corrected all in gbrp so every plane gets the same weight: see 975 (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#maskedmerge, checked 2026-10-24]
973. **HSL qualifier = a colour key** — the HSL qualifier keys any hue/sat/luma range (not just green/blue) from eyedropper samples. It is fastest for irregular subjects with a distinct colour, and needs no tracking. **How:** ffmpeg `hsvkey` (hue, sat, val, similarity, blend) makes the alpha. Pull it with `alphaextract`. [Resolve 18 manual, https://www.steakunderwater.com/VFXPedia/__man/Resolve18-6/DaVinciResolve18_Manual_files/part2809.htm, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#hsvkey, checked 2026-10-24]
974. **Matte finesse moves** — Clean Black fills holes in the background, Clean White fills holes in the foreground, and Blur Radius/In-Out Ratio soften and push the edge. Key denoise reduces chattering over time. Heavy cleanup can kill soft edges and big blur can halo. **How:** soften the ffmpeg matte with `gblur=sigma=3..6`, and calm chatter with `tmix=frames=3` on the mask (both tested here 2026-10-24) [Resolve 18 manual, https://www.steakunderwater.com/VFXPedia/__man/Resolve18-6/DaVinciResolve18_Manual_files/part2809.htm, checked 2026-10-24] [Blackmagic Forum, https://forum.blackmagicdesign.com/viewtopic.php?f=21&t=178630, checked 2026-10-24] [videomontazher, https://videomontazher.com/en/color/qualifier-windows-tracker, checked 2026-10-24]
975. **Qualifier secondary in one ffmpeg graph** — key a hue range, invert to the wanted part, soften, and merge a corrected copy through the mask. **How:** `ffmpeg -i in.mp4 -filter_complex "[0:v]split[a][b];[b]format=yuva444p,hsvkey=hue=0:sat=0.7:val=0.6:similarity=0.25:blend=0.1,alphaextract,negate,gblur=sigma=3,format=gbrp[m];[a]format=gbrp,split[o][g];[g]huesaturation=saturation=0.4[gr];[o][gr][m]maskedmerge,format=yuv420p" out.mp4` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#hsvkey, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#maskedmerge, checked 2026-10-24]
976. **Luma qualifier for range-specific colour** — the LUM qualifier mode targets ranges of lightness. Colourists use it to change colour temperature in highlights or shadows only. **How:** ffmpeg `lumakey=threshold=1:tolerance=0.3:softness=0.1` → alphaextract → negate → maskedmerge with a `colortemperature` copy (tested here 2026-10-24) [DaVinci Resolve 12 manual, https://ltbits.github.io/davinci-resolve-manuals/DR12/DR12-RM-27.pdf, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#lumakey, checked 2026-10-24]
977. **Power window shapes** — Resolve offers linear, circle, polygon, curve and gradient windows, each with softness, invert and subtract. Windows give clean, precise edges for faces, car fronts and skies. **How:** draw a soft ellipse mask with geq: `nullsrc=s=640x360:d=2,geq=lum='255*clip(1.5-hypot((X-W/2)/(W*0.25),(Y-H/2)/(H*0.35)),0,1)',format=gray,format=gbrp` (tested here 2026-10-24) [JayAreTV, https://jayaretv.com/color/davinci-resolve-power-windows-explained/, checked 2026-10-24] [DaVinci Resolve 11 manual, https://ltbits.github.io/davinci-resolve-manuals/DR11/DR11-RM-12.pdf, checked 2026-10-24]
978. **Gradient window = graduated filter** — the gradient window works like a graduated filter, e.g. for a sky. **How:** mask `geq=lum='255*clip(Y/(H*0.5),0,1)'` merging a darker copy over the top half (tested here 2026-10-24) [JayAreTV, https://jayaretv.com/color/davinci-resolve-power-windows-explained/, checked 2026-10-24]
979. **Windows must follow motion** — Power Windows have to be animated or tracked to follow the subject. **How:** without a tracker in ffmpeg, move the geq mask with T: `geq=lum='255*clip(1.5-hypot((X-(W*0.3+T*100))/(W*0.2),(Y-H/2)/(H*0.3)),0,1)'` (tested here 2026-10-24); a real track needs a tracker (Missing tools) [DaVinci Resolve 11 manual, https://ltbits.github.io/davinci-resolve-manuals/DR11/DR11-RM-12.pdf, checked 2026-10-24]
980. **Fix the grade first, isolate skin after** — Noam Kroll: balance and match shots with one or two technical nodes first, then isolate elements like skin. Don't build the whole grade around skin and neglect everything else. **How:** run primaries on the whole clip, then a qualifier pass (975) for skin. [Noam Kroll, https://noamkroll.com/how-to-match-skintones-perfectly-using-qualifiers-power-windows-in-davinci-resolve/, checked 2026-10-24]
981. **Window plus qualifier for skin** — when a skin key also grabs similar background colours, a circular window limits it to the person. **How:** multiply the hsvkey matte by an ellipse geq mask (`blend=all_mode=multiply`) before maskedmerge. The blend step is not tested here. [DaVinci Resolve 11 manual, https://ltbits.github.io/davinci-resolve-manuals/DR11/DR11-RM-12.pdf, checked 2026-10-24]
982. **Check the matte, then the picture** — alternate matte view and normal view, since a perfect black-and-white mask doesn't guarantee an invisible correction. Diagnose leaks, noise, geometry or track drift first. **How:** render the mask branch alone (`-map` the `[m]` output) for a few frames and look at it. [videomontazher, https://videomontazher.com/en/color/qualifier-windows-tracker, checked 2026-10-24]

## Shot matching

983. **Pick a technically sound hero shot** — Frame.io: the hero should represent the scene (often a wide) and must not be badly exposed or cast. Match the others to it in a comparison view, scene by scene. **How:** compare side by side with `ffmpeg -i hero.mp4 -i shot.mp4 -filter_complex "[0:v][1:v]hstack" out.mp4` (tested here 2026-10-24) [Frame.io Workflow Guide, https://workflow.frame.io/guide/primary-color-correction, checked 2026-10-24]
984. **Match by numbers** — compare YAVG/UAVG/VAVG (and YLOW/YHIGH) of hero and shot, then move levels/balance until they agree. **How:** loop signalstats over both files: `ffmpeg -i f.mp4 -vf "signalstats,metadata=mode=print:file=m.txt" -frames:v 1 -f null -` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#signalstats, checked 2026-10-24]
985. **Colour-patch mapping with colormap** — colormap takes the video plus source and target patch streams (e.g. a chart shot under each camera) and maps colours (up to 64 patches, relative or absolute, euclidean/weuclidean kernel). **How:** `ffmpeg -i in.mp4 -i src_chart.png -i tgt_chart.png -filter_complex "[1]loop=-1:1:0[s];[2]loop=-1:1:0[d];[0][s][d]colormap=patch_size=64x64:nb_patches=24:type=relative[o]" -map "[o]" -t 2 out.mp4` (tested here 2026-10-24 with ffmpeg colorchart images) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#colormap, checked 2026-10-24]
986. **Histogram matching in Python** — skimage `match_histograms(image, reference, channel_axis=-1)` matches each channel's cumulative histogram to a reference. Wikipedia: it suits two images of the same place under different sensors or light. **How:** `/home/user/tools/venv/bin/python -I -c "from skimage import io; from skimage.exposure import match_histograms; ..."` on exported frames (tested here 2026-10-24) [scikit-image docs, https://scikit-image.org/docs/stable/api/skimage.exposure.html, checked 2026-10-24] [Wikipedia, https://en.wikipedia.org/wiki/Histogram_matching, checked 2026-10-24]
987. **Match HLG and SDR cameras scene-referred** — BT.2408: use scene-referred mapping to match BT.709/BT.2020 SDR cameras with HLG cameras, because both signals represent scene light. Display-referred mapping would make them mismatch. **How:** when mixing phone HLG with SDR clips, convert the SDR into HLG scene-light, not by look. [ITU-R BT.2408-5, https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2408-5-2022-PDF-E.pdf, checked 2026-10-24]
988. **Skin can drift after shots are balanced** — lenses and lighting differ, so skin can still differ between shots after primaries. Colourists isolate skin and match it as a separate step. **How:** a skin qualifier pass (975) per shot after the hero match. [Noam Kroll, https://noamkroll.com/how-to-match-skintones-perfectly-using-qualifiers-power-windows-in-davinci-resolve/, checked 2026-10-24] [Mixing Light, https://mixinglight.com/color-tutorial/shot-matching-working-skintone, checked 2026-10-24]
989. **Grade the group, not each clip, afterwards** — once shots share a baseline, Frame.io says global changes go on an adjustment layer, node or nested sequence for all of them at once. **How:** in ffmpeg, apply the same baked Hald/cube (967) to every matched clip. [Frame.io Workflow Guide, https://workflow.frame.io/guide/primary-color-correction, checked 2026-10-24]

## HDR: formats, metadata, encoding

990. **PQ basics** — SMPTE ST 2084 (Dolby, 2014, BT.2100 in 2016): signal 0–1 = 0–10,000 cd/m², absolute. No visible banding at 12 bits, where a power law would need 15. Base of HDR10, HDR10+ and Dolby Vision. Not backward compatible with BT.1886. **How:** tag `transfer=smpte2084`. [Wikipedia, https://en.wikipedia.org/wiki/Perceptual_Quantizer, checked 2026-10-24]
991. **PQ code values for common levels** — computed from the ST 2084 inverse EOTF: 100 cd/m² ≈ 0.508, 203 ≈ 0.581, 1000 ≈ 0.752 of signal. **How:** `python3` with m1=2610/16384, m2=2523/4096·128, c1=3424/4096, c2=2413/4096·32, c3=2392/4096·32 (tested here 2026-10-24; 203 → 58%, matching BT.2408's 58% PQ) [Wikipedia, https://en.wikipedia.org/wiki/Perceptual_Quantizer, checked 2026-10-24] [ITU-R BT.2408-7, https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2408-7-2023-PDF-E.pdf, checked 2026-10-24]
992. **HLG basics** — BBC/NHK, ARIB STD-B67, in BT.2100. The lower half of the signal is a gamma (square-root) curve and the upper half logarithmic. No metadata. Reference white sits at signal 0.5. Royalty-free. **How:** tag `transfer=arib-std-b67` with bt2020 primaries and 10-bit. [Wikipedia, https://en.wikipedia.org/wiki/Hybrid_log%E2%80%93gamma, checked 2026-10-24] [Encode Wiki, https://encode.wiki/hdr/, checked 2026-10-24]
993. **HLG on SDR screens** — HLG is backward compatible with SDR UHDTV that understands BT.2020. On Rec.709-only displays it looks desaturated with hue shifts, so broadcasters do a colour space conversion for HD simulcast. **How:** tone-map/convert phone HLG before sharing to SDR-only platforms. [Wikipedia, https://en.wikipedia.org/wiki/Hybrid_log%E2%80%93gamma, checked 2026-10-24] [BBC HDR FAQ, https://downloads.bbc.co.uk/rd/pubs/papers/HDR/BBC_HDRTV_FAQ.pdf, checked 2026-10-24]
994. **HDR format table** — HDR10 = PQ + static ST 2086 + MaxCLL/MaxFALL. HDR10+ = HDR10 + per-scene ST 2094-40. Dolby Vision = PQ (profiles 5, 7, 8.1, 10.1) or HLG (8.4) + per-frame RPU. HLG = no metadata. **How:** identify with the two ffprobe commands (801/802). [Encode Wiki, https://encode.wiki/hdr/, checked 2026-10-24]
995. **Identify HDR flavour from ffprobe output** — smpte2084 + mastering + content light = HDR10. Plus "HDR Dynamic Metadata SMPTE2094-40" = HDR10+. "DOVI configuration record" = Dolby Vision (dv_profile/compat id). arib-std-b67 = HLG. dv_profile=5 with unknown/ipt-c2 tags = DV profile 5. **How:** grep ffprobe `-show_frames` and `-show_streams` output. [Encode Wiki, https://encode.wiki/hdr/, checked 2026-10-24]
996. **iPhone HDR is Dolby Vision 8.4 on HLG** — Apple records DV profile 8, cross-compatibility ID 4 (HLG), 10-bit HEVC, so plain HEVC decoders see HLG. **How:** treat iPhone HDR clips as HLG in ffmpeg chains (`tin=arib-std-b67`). [Apple Developer, https://developer.apple.com/av-foundation/Incorporating-HDR-video-with-Dolby-Vision-into-your-apps.pdf, checked 2026-10-24]
997. **DV profile 5 looks green/purple without DV** — profile 5's base layer is proprietary IPTPQc2, so without Dolby Vision processing colours are wrong (green/purple). The zscale+tonemap chain ignores DV metadata. **How:** profile 5 needs libplacebo (applies RPUs, needs Vulkan, missing here). [Encode Wiki, https://encode.wiki/hdr/, checked 2026-10-24]
998. **HDR10 static metadata units** — mastering display primaries/white in units of 0.00002 and luminance in 0.0001 cd/m². MaxCLL = brightest pixel, MaxFALL = highest frame average, both in cd/m². **How:** x265 string `G(13250,34500)B(7500,3000)R(34000,16000)WP(15635,16450)L(10000000,1)` is P3-D65, 1000 / 0.0001 nits. [x265 docs, https://x265.readthedocs.io/en/master/cli.html, checked 2026-10-24] [Microsoft Learn, https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/iddcx/ns-iddcx-iddcx_hdr10_metadata, checked 2026-10-24]
999. **Encode HDR10 with x265 inside ffmpeg** — set the VUI tags plus master-display, max-cll, hdr10-opt (block QP tuning for PQ, use with AQ) and repeat-headers. **How:** `ffmpeg -i in.mp4 -c:v libx265 -pix_fmt yuv420p10le -x265-params "colorprim=bt2020:transfer=smpte2084:colormatrix=bt2020nc:master-display=G(13250,34500)B(7500,3000)R(34000,16000)WP(15635,16450)L(10000000,1):max-cll=1000,400:hdr10-opt=1:repeat-headers=1" out.mp4` (tested here 2026-10-24; ffprobe showed both side data blocks) [x265 docs, https://x265.readthedocs.io/en/master/cli.html, checked 2026-10-24] [Encode Wiki, https://encode.wiki/guides/preserve-color-and-hdr, checked 2026-10-24]
1000. **Copy HDR10 numbers from the source, never invent them** — the mastering peak is a property of the grade and MaxCLL/MaxFALL are measured from content. When a source has none, leave them out. **How:** read the fractions from ffprobe frame side data (802) and convert ×50000 / ×10000 for x265. [Encode Wiki, https://encode.wiki/guides/preserve-color-and-hdr, checked 2026-10-24]
1001. **One glint sets MaxCLL** — MaxCLL is one number for the whole file from its brightest pixel, so a single specular highlight can set it. MaxFALL is the average-facing value. Dolby Vision/HDR10+ exist because static values can't fit both dark and bright scenes. **How:** don't panic at a high MaxCLL, and check MaxFALL for overall brightness. [SDRtoHDR, https://sdrtohdr.com/glossary/maxcll, checked 2026-10-24] [HDfury, https://www.hdfuryvertex.com/glossary/hdr10.html, checked 2026-10-24]
1002. **Read MaxCLL with ffprobe** — the frame side data fields max_content and max_average are MaxCLL and MaxFALL. **How:** `ffprobe -v error -select_streams v:0 -show_frames -read_intervals "%+#1" -show_entries frame_side_data=max_content,max_average -of default=nw=1 in.mp4` [SDRtoHDR, https://sdrtohdr.com/glossary/maxcll, checked 2026-10-24]
1003. **HLG encode: no HDR10 metadata** — encode HLG 10-bit with bt2020/bt2020nc/arib-std-b67 and don't add mastering metadata unless the source has it. x265 also offers `atc-sei` and `pic-struct`, which it marks "required for HLG signalling". **How:** `-x265-params "colorprim=bt2020:transfer=arib-std-b67:colormatrix=bt2020nc:atc-sei=18:pic-struct=0"` (tested here 2026-10-24) [Encode Wiki, https://encode.wiki/hdr/, checked 2026-10-24] [x265 docs, https://x265.readthedocs.io/en/master/cli.html, checked 2026-10-24]
1004. **ffmpeg 7.0+ passes HDR10 metadata through; 6.1 here did not** — Encode Wiki: since 7.0 a plain transcode passes mastering and content-light metadata to libx264/libx265/libsvtav1. Here (6.1) the SDR output of a PQ file carried no mastering metadata. **How:** on 6.1, re-add HDR10 values with -x265-params when re-encoding HDR (ffprobe check tested here 2026-10-24) [Encode Wiki, https://encode.wiki/guides/preserve-color-and-hdr, checked 2026-10-24]
1005. **HDR10+ and Dolby Vision need extra tools** — libx265 drops HDR10+: extract with hdr10plus_tool and pass `dhdr10-info=metadata.json`. Dolby Vision: `-dolbyvision 1` with libx265 writes profile 8.x (needs VBV), or extract the RPU with dovi_tool. Profile 7 must be converted to 8.1 first. **How:** needs hdr10plus_tool and dovi_tool (missing). [Encode Wiki, https://encode.wiki/guides/preserve-color-and-hdr, checked 2026-10-24] [x265 docs, https://x265.readthedocs.io/en/master/cli.html, checked 2026-10-24]
1006. **YouTube HDR upload spec** — 10 or 12 bit. Rec.2020 primaries, Rec.2020 NCL matrix, PQ or HLG. PQ files should carry ST 2086 and MaxCLL/MaxFALL, or YouTube assumes a Sony BVM-X300. Recommended codecs VP9 Profile 2, AV1, HEVC. ProRes/DNxHR/10-bit H.264 work at high bitrates. **How:** encode with 999 (PQ) or 1003 (HLG). [YouTube Help, https://support.google.com/youtube/answer/7126552?hl=en, checked 2026-10-24]
1007. **PQ shadows hold hidden noise** — YouTube: PQ spends much of its range on shadows, so dark noise masked by highlights may be cleaned (or look compressed) after upload. Denoise before rendering for more control. **How:** denoise the HDR master before the x265 pass. [YouTube Help, https://support.google.com/youtube/answer/7126552?hl=en, checked 2026-10-24]
1008. **HDR reference monitor targets (Netflix)** — SDR: Rec.709, D65, BT.1886 gamma 2.4, ≤0.05 nit black, 100 nits, 2000:1. Dolby Vision HDR: P3, D65, PQ, 0.005 nit black, 1000 nits, 200,000:1. 1009. **Netflix HDR originals master in Dolby Vision** — Netflix derives Dolby Vision, HDR10 and SDR streams from one Dolby Vision IMF. ## HDR conversions in ffmpeg

1010. **Washed-out grey = curve mismatch, not a bad encode** — a naive `scale,format=yuv420p` reads PQ/HLG codes as SDR gamma and squeezes BT.2020 into BT.709 with no tone map, so the clip looks grey. Higher bitrate changes nothing. **How:** always tone-map (1011). [ffmpeg-micro, https://www.ffmpeg-micro.com/blog/ffmpeg-hdr-to-sdr-stop-iphone-uploads-coming-out-gray, checked 2026-10-24] [ez-ffmpeg docs, https://docs.rs/ez-ffmpeg/latest/ez_ffmpeg/core/recipes/index.html, checked 2026-10-24]
1011. **Strip HDR side data after tone mapping** — Encode Wiki: ffmpeg passes mastering/content-light metadata to the encoder even after tone mapping, so the SDR file still claims HDR. Delete it in the chain. **How:** `ffmpeg -i hdr.mkv -vf "zscale=t=linear:npl=100,format=gbrpf32le,zscale=p=bt709,tonemap=hable:desat=0,zscale=t=bt709:m=bt709:r=tv,format=yuv420p,sidedata=mode=delete:type=MASTERING_DISPLAY_METADATA,sidedata=mode=delete:type=CONTENT_LIGHT_LEVEL" -c:v libx264 -crf 18 sdr.mkv` (tested here 2026-10-24) [Encode Wiki, https://encode.wiki/hdr/, checked 2026-10-24] [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#sidedata_002c-asidedata, checked 2026-10-24]
1012. **npl sets what becomes SDR white** — `npl=100` maps 100 cd/m² in the source to SDR white. Encode Wiki says raising it darkens the result. The media-os guide says raising it brightens. **How:** measured here on an HLG clip through the hable chain: YAVG 77 at npl=100 and 64 at npl=400, so higher npl = darker (tested here 2026-10-24) [Encode Wiki, https://encode.wiki/hdr/, checked 2026-10-24] [media-os skill, https://github.com/damionrashford/media-os/blob/main/skills/ffmpeg-hdr-color/SKILL.md, checked 2026-10-24]
1013. **Tell zscale the HLG input curve** — for HLG sources one guide sets `tin=arib-std-b67` in the linearising zscale. **How:** `ffmpeg -i hlg.mp4 -vf zscale=t=linear:tin=arib-std-b67:npl=100,format=gbrpf32le,zscale=p=709,tonemap=hable:desat=0,zscale=t=709:m=709:r=limited:d=error_diffusion,format=yuv420p -c:v libx264 out.mp4` (tested here 2026-10-24) [media-os skill, https://github.com/damionrashford/media-os/blob/main/skills/ffmpeg-hdr-color/SKILL.md, checked 2026-10-24]
1014. **tonemap operators per the docs** — clip: perfect accuracy in range, distorts out of range. linear: stretch by param. gamma: log fit (param default 1.8). reinhard: keeps overall brightness, flattens detail (param default 0.5). hable: keeps dark and bright detail, slightly darkens. mobius: keeps in-range colour (param default 0.3 = linear-to-mobius transition). **How:** e.g. `tonemap=reinhard:param=0.5:desat=2` and `tonemap=clip` (both tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#tonemap, checked 2026-10-24]
1015. **tonemap desat and peak** — `desat` (default 2.0) turns super-highlights toward white, and 0 disables it. `peak` overrides the signal peak when embedded metadata is unreliable. **How:** `tonemap=mobius:param=0.3:peak=10` (tested here 2026-10-24) [ffmpeg docs, https://ffmpeg.org/ffmpeg-filters.html#tonemap, checked 2026-10-24]
1016. **Automatic tone mapping is a compromise** — a fixed curve that suits one scene clips or dulls another, so watch the result on an SDR display. An official SDR version, when it exists, is usually better. **How:** ask the client for their SDR master before converting HDR yourself. [Encode Wiki, https://encode.wiki/hdr/, checked 2026-10-24]
1017. **libplacebo is the higher-quality path (needs Vulkan)** — libplacebo does tone and gamut mapping in one filter, uses mastering metadata, does peak detection (`peak_detect`, `percentile` default 99.995), offers tonemapping like `bt.2390`/`spline` and gamut modes (perceptual default, clip, relative, saturation, darken, warn ...), and applies DV RPUs. **How:** needs a Vulkan device. Here `-init_hw_device vulkan` failed (VK_ERROR_INCOMPATIBLE_DRIVER), so it is missing. [Encode Wiki, https://encode.wiki/hdr/, checked 2026-10-24] [ffmpeg 8.0 docs mirror, https://ayosec.github.io/ffmpeg-filters-docs/8.0/Filters/Video/libplacebo.html, checked 2026-10-24] [libplacebo options, https://libplacebo.org/options/, checked 2026-10-24]
1018. **HLG→PQ is transcode vs convert** — BT.2408: a transcode (HLG EOTF → PQ inverse EOTF) gives identical light only on a display of the same peak, and diffuse white moves with the assumed HLG display peak. Converting at a 1000 cd/m² reference keeps brightness consistent. Avoid cascaded conversions. **How:** `ffmpeg -i hlg.mp4 -vf zscale=tin=arib-std-b67:t=smpte2084:npl=1000,format=yuv420p10le -c:v libx265 -x265-params colorprim=bt2020:transfer=smpte2084:colormatrix=bt2020nc out.mp4` ran here (tested here 2026-10-24); whether zscale applies the 1000-nit reference OOTF was not verified. [ITU-R BT.2408-7, https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2408-7-2023-PDF-E.pdf, checked 2026-10-24]
1019. **SDR→HDR10 mapping (MovieLabs)** — decode SDR with BT.1886 (gamma 2.4, Lw 100, Lb 0), convert BT.709→BT.2020 (BT.2087 M2), multiply linear light by 2.0 (white → 200 cd/m²), encode with PQ inverse EOTF. Metadata: BT.709 primaries, mastering max 200 / min 0, MaxCLL 200, MaxFALL 0 (unknown). **How:** steps only. No ffmpeg chain for this was verified here (a zscale attempt failed). [MovieLabs, https://MovieLabs.com/wp-content/uploads/2018/04/MovieLabs_Mapping_BT.709_to_HDR10_v1.0-2.pdf, checked 2026-10-24]
1020. **Put SDR graphics at Graphics White** — BT.2408: map SDR graphics directly at 75% HLG / 58% PQ so they don't look too bright and dull the video. Use display-light mapping to keep brand colours, scene-light mapping to match in-scene signs. **How:** check title cards on the HDR waveform against 58% PQ. [ITU-R BT.2408-7, https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2408-7-2023-PDF-E.pdf, checked 2026-10-24]
1021. **White subtitles in HDR at ≥75%** — ZDF's grading guideline asks pure white text (subtitles, credits) be at least 75% (203 cd/m² on a 1000 cd/m² monitor), adjusted to the background. **How:** same check as 1020 for captions on HDR deliveries. [ZDF Grading Guidelines, https://www.zdf.de/assets/english-version-grading-100~original?cb=1787523489761, checked 2026-10-24]
1022. **PQ on a BT.709 monitor looks dim and washed out** — BT.2408: PQ fed to a BT.709 monitor is dim, desaturated and hue-shifted. A down-mapping 3D LUT allows viewing but not critical HDR judgement. **How:** preview HDR here only through a tone-mapped proxy, and label it so. [ITU-R BT.2408-7, https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2408-7-2023-PDF-E.pdf, checked 2026-10-24]
1023. **Check SDR derived from HDR for detail loss** — static HDR→SDR down-mappers are tuned to reference levels. Content far from HDR Reference White can lose detail (skin, text) in the derived SDR. **How:** after 1011, look at faces and captions on the SDR waveform. [ITU-R BT.2408-7, https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2408-7-2023-PDF-E.pdf, checked 2026-10-24]

## ACES, OCIO and colour space transforms

1024. **ACES pipeline parts** — Input Transform (IDT: camera → ACES), Reference Rendering Transform (RRT: scene → display-referred with an S-curve), Output Device Transform (ODT: to Rec.709/P3/Rec.2020). In practice RRT+ODT are combined as the Output Transform. **How:** map these names to the CST/LUT steps you do in ffmpeg (conversion LUT = input, look, display LUT = output). [Autodesk Arnold docs, https://help.autodesk.com/cloudhelp/2024/ENU/AR-Maya/files/am-Arnold_for_Maya_User_Guide/rendering/arnold_for_maya_rendering_am_ACES_Workflow_html.html, checked 2026-10-24] [ACES docs, https://docs.acescentral.com/system-components/output-transforms/, checked 2026-10-24]
1025. **ACES colour spaces** — ACES2065-1: linear, AP0, archive/interchange. ACEScg: linear AP1 for CG/VFX. ACEScc/ACEScct: log AP1 for grading. ACEScct adds a toe like film log, which gives a milky lift in shadows. ACES white is (0.32168, 0.33767). **How:** grade in ACEScct, render CG in ACEScg. [ACESCentral, https://acescentral.com/knowledge-base-2/aces-working-spaces/, checked 2026-10-24] [Autodesk Arnold docs, https://help.autodesk.com/cloudhelp/2024/ENU/AR-Maya/files/am-Arnold_for_Maya_User_Guide/rendering/arnold_for_maya_rendering_am_ACES_Workflow_html.html, checked 2026-10-24]
1026. **ACES transform types** — CSC (colour space conversion), Input, Output (RRT+ODT, token RRTODT before ACES 2), InvOutput (display-referred back to ACES), Look (LMT). **How:** an inverse output transform is how you bring a finished Rec.709 graphic into an ACES grade. [ACES docs, https://docs.acescentral.com/system-components/transform-id-spec/, checked 2026-10-24]
1027. **Netflix ACES settings in Resolve** — use ACEScct unless you need ACEScc. ODT Rec.709 for SDR (100 nit BT.1886 monitor), P3-D65 ST2084 (1000 nits) for HDR. Keep ACES Mid Gray Luminance at 15.00. ODT None outputs ACES2065-1. **How:** follow for any client asking for an ACES Resolve project. [Netflix Partner Help, https://partnerhelp.netflixstudios.com/hc/en-us/articles/360002088888-Color-Managed-Workflow-in-Resolve-ACES, checked 2026-10-24]
1028. **ffmpeg is weak at colour space conversion** — the ORI encoding guidelines recommend OCIO-based tools (Nuke, oiiotool, or the ffmpeg OCIO filter) with the ACES config, writing PNG/TIF/DPX intermediates for ffmpeg. **How:** `oiiotool ... --colorconvert acescg srgb --dither -o out.#.png` (needs oiiotool, missing) [ORI Encoding Guidelines, https://academysoftwarefoundation.github.io/EncodingGuidelines/EncodingOverview.html, checked 2026-10-24]
1029. **ffmpeg 8.1 OCIO filter** — `ocio=input=...:output=...` or `display=...:view=...` with built-in configs like `ocio://studio-config-v1.0.0_aces-v1.3_ocio-v2.1`. Output format must be RGB (rgb48, gbrpf32le ...), then convert to YCbCr with scale. **How:** needs ffmpeg 8.1 built with libopencolorio (missing; local is 6.1) [ORI Encoding Guidelines, https://academysoftwarefoundation.github.io/EncodingGuidelines/FfmpegOcio.html, checked 2026-10-24] [ffmpeg 8.1 docs mirror, https://ayosec.github.io/ffmpeg-filters-docs/8.1/Filters/Video/ocio.html, checked 2026-10-24]
1030. **CST is a signal contract** — Resolve's Color Space Transform has four fields (input space, input gamma, output space, output gamma) that must describe the real signal. Take camera gamut/log from metadata or documentation, not from how contrasty the viewer looks. **How:** the same rule for picking an ffmpeg conversion LUT: confirm the camera profile first. [videomontazher, https://videomontazher.com/en/color/resolve-fx/color-space-transform, checked 2026-10-24]
1031. **Tone mapping ≠ gamut mapping** — in a CST, tone mapping handles luminance/dynamic range (Clip, Simple, Luminance Mapping, DaVinci, Saturation Preserving) and gamut mapping handles colours outside the target gamut. Check one on the waveform, the other on vectorscope/CIE. **How:** after an ffmpeg HDR→SDR chain, check waveform (894) and ciescope (880) separately. [videomontazher, https://videomontazher.com/en/color/resolve-fx/color-space-transform, checked 2026-10-24]
1032. **CST Clip vs Luminance Mapping** — a forum explanation: Clip leaves in-gamut colours unchanged and flattens out-of-gamut ones to the edge (detail lost). Luminance Mapping brings everything in, so in-gamut colours like skin also shift slightly. **How:** expect the same trade-off between `tonemap=clip` and the curve operators. [Blackmagic Forum, https://forum.blackmagicdesign.com/viewtopic.php?f=21&t=212648, checked 2026-10-24]
1033. **One colourist's output CST settings** — Frame.io author: Tone Mapping = Luminance Mapping, Custom Max Input 10,000 nits, Max Output 100, Gamut Mapping = Saturation Compression, Apply Forward OOTF on, so highlights decelerate instead of clipping. **How:** Resolve-only. Use as a starting point when a client sends a Resolve project. [Frame.io Insider, https://blog.frame.io/2024/01/08/color-management-nodes-davinci-resolve/, checked 2026-10-24]
1034. **Grade before the output transform** — forum advice: in a wide timeline space (DWG/Intermediate) the output CST's tone mapping catches highlights, so pushing gain before the CST blows out less than after it. **How:** in ffmpeg, put exposure/levels before the log→709 LUT, not after. [Blackmagic Forum, https://forum.blackmagicdesign.com/viewtopic.php?f=21&t=205523, checked 2026-10-24]
1035. **RCM vs ACES** — both are scene-referred colour management for the same problem. Resolve Color Management is simpler outside ACES-mandated work and keeps the familiar control feel. RCM also helps editors: assign each log clip its Input Color Space and it looks normal. **How:** for a Resolve client, assign input spaces per camera instead of LUT-ing in the timeline. [Resolve 18 manual, https://www.steakunderwater.com/VFXPedia/__man/Resolve18-6/DaVinciResolve18_Manual_files/part284.htm, checked 2026-10-24]
1036. **Timeline colour space changes how tools feel** — Resolve: Rec.709 feels familiar for SDR, and log/wide spaces (Cineon, LogC, DWG) suit film-style workflows. For HDR delivery choose a wide space. Default Input Color Space doesn't affect RAW or clips with embedded colour metadata. **How:** decide the working space before grading, and don't switch mid-project. [Resolve 18 manual, https://www.steakunderwater.com/VFXPedia/__man/Resolve18-6/DaVinciResolve18_Manual_files/part294.htm, checked 2026-10-24]

## Mac/QuickTime and web display quirks

1037. **QuickTime plays 1-1-1 video at gamma ~1.96** — AVFoundation uses ~1.96 as video gamma (2.45/1.25) and converts to the 2.2 display buffer on macOS 10.6+. A 75% grey bar (191) reads ~198 on screen. Pixel values read off the screen differ from the file. **How:** don't judge Mac QuickTime screenshots as truth, and judge with scopes on decoded frames. [Apple TN2257, https://developer.apple.com/library/archive/technotes/tn2257/_index.html, checked 2026-10-24] [ACESCentral, https://community.acescentral.com/t/gamma-shift/4633, checked 2026-10-24]
1038. **Resolve 1-2-1 tags and re-encoders** — Resolve exports Rec.709 gamma 2.4 timelines with 1-2-1 tags. With "Use Mac Display Color Profiles for Viewers" on (after macOS 10.14.6), QuickTime matches the viewer. Re-encoding with HandBrake turns tags into 1-1-1 and the match breaks. **How:** the article ties the QuickTime match to the 1-2-1 tag, so check with ffprobe that a re-encode still has color_transfer unknown (2) before sending it to a Mac client. [The Post Process, https://www.thepostprocess.com/2020/07/17/color-on-mac-displays-from-davinci-resolve-to-the-internet-with-quicktime-tags/, checked 2026-10-24]
1039. **Display P3 EDR on Macs** — Apple calls Display P3 values above nominal white EDR, which Resolve and Nuke use to show HDR on Mac screens. **How:** an HDR preview on a MacBook is EDR, not a reference HDR monitor. [Antler Post, https://antlerpost.com/colour-spaces/P3D65.html, checked 2026-10-24]
1040. **Tagged colour bars test a player** — Apple's QuickTime Test Pattern files test black crush, gradients, 100%/75% bars (matrix) and quantised gradient (gamma), and the bars themselves must be nclc-tagged. **How:** make tagged bars with ffmpeg: `ffmpeg -f lavfi -i smptehdbars=size=1280x720 -t 2 -c:v libx264 -color_primaries bt709 -color_trc bt709 -colorspace bt709 bars.mp4` (only the smptehdbars source was tested here) and check them in the client's player. [Apple TN2257, https://developer.apple.com/library/archive/technotes/tn2257/_index.html, checked 2026-10-24]
